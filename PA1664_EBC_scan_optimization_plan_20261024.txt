一、结论摘要
======================================================================
当前问题不能简单归因于“CPU 平均占用太高”。更可能的根因是：

1. 超声解码线程通过 Qt::DirectConnection 同步执行 UI 合并和缓存合并，容易被下游锁/UI 长尾拖住。
2. 编码器 C 扫描 FIFO 只有 1024 个包。按代码注释中的 8 kHz 估算，大约只有 128 ms 缓冲；一旦解码线程停顿超过这个余量，就会丢掉最老的编码器包。
3. CScan FIFO 满时直接 dequeue，但没有增加 C 扫描丢包计数，所以当前显示的 FPS/丢帧统计不能证明 B/C 扫描完整。
4. MainWindow 的 UI 合并表限制为 4096 个 key，超过时删除最老项且没有计数。切页造成 GUI 卡顿时，UI 自己也可能丢 B/C 数据。
5. CScanWidget::paintEvent 每次重新创建完整 raster，并遍历当前 gate 的全部 cell；单 gate 最多 262,144 个 cell。切页会触发明显 GUI 长尾。
6. B 扫动态缩放变化时可能全图 rebuild，页面切换或参数变化也可能造成额外重绘。
7. 小车控制虽然有独立线程，但仍与超声、UI、缓存写盘共享同一进程和 CPU。平均 CPU 不高不代表关键线程没有调度抖动。

推荐路线：
P0 可观测性 -> P1 修队列和同步 fan-out -> P2 拆 UI/缓存/绘制 -> P3 抽超声后端接口 -> P4 独立超声服务进程 -> P5 可选运动服务隔离。

不建议直接做 P4。只搬 DeviceController 不够，因为 ParameterPanel、ParameterPresetStore、PulseLoadGuard、RemoteControlServer、MainWindow 和 main.cpp 都直接使用 Client 或 SDK 生命周期逻辑。


二、现场现象与证据边界
======================================================================
此前只读采样看到：
- PA1664Workbench.exe 约 37 个线程，工作集约 159-163 MB。
- 机器为 Intel Core Ultra 5 225H，14 个逻辑处理器。
- 采样时整机负载约 20%。
- 日志曾出现 invalid physical device id -1，说明当时超声没有真实在线流量。

因此：
- 那次采样不能证明“CPU 一定够”或“CPU 一定不够”。
- 但代码结构足以支持以下判断：这不是单纯算力总量问题，更可能是关键路径停顿、锁竞争、队列容量和 GUI 长尾问题。
- 最终必须用真实超声在线、真实 B/C 扫描、真实纠偏和真实切页的数据确认。


三、当前完整链路
======================================================================
3.1 超声采集和扫描

厂商 SDK 回调线程
  -> DeviceController::packetCallback
  -> 同一把 m_frameMailboxMutex
     -> Display FIFO：36 包，显示延迟目标 30 帧
     -> CScan FIFO：1024 包，约 128 ms
  -> FrameDecoderWorker 解码线程
     -> 33 ms 显示解码
     -> 有 B/C 时改为 5 ms PreciseTimer
  -> groupScanBatchDecoded
     -> DirectConnection -> MainWindow::enqueueGroupScanBatch
     -> DirectConnection -> ScanWaveformCache::enqueueBatch
  -> GUI 20 ms drain
  -> acceptGroupScanBatch
  -> BScanWidget / CScanWidget 更新和重绘

3.2 小车和纠偏

RobotControlPanel 已有多个独立 QThread：
- 驱动控制线程：SynchronizedDriveController，20 ms PreciseTimer
- 传感器/IMU/激光相机线程：RobotSensorController，相机 5 ms PreciseTimer
- 激光纠偏线程：LaserCorrectionController，20 ms PreciseTimer watchdog
- 轮廓检测日志线程
- 轨迹写盘线程
- USB 相机线程
- UI 侧 80 ms 运动命令定时器

问题不是“小车没有线程”，而是这些线程仍与超声解码、UI、缓存共享同一个进程资源。

3.3 切页实际影响

m_workspace 是 QTabWidget。当前没有看到切页时主动销毁超声解码线程的代码。
切页会触发：
- 页面隐藏/显示
- 布局重新计算
- B/C/E 图谱重绘
- 状态栏/标签排版
- 解码线程同步入队与 GUI drain 的竞争

双窗口布局下，窗口失活还可能触发 RobotControlPanel::changeEvent 中的 stopAutoCorrection()。这是现有安全行为，需要单独确认和保留。

五、根因优先级
======================================================================
P0：解码线程同步 fan-out + CScan FIFO 余量不足 + C 扫丢包不可见
P1：UI 侧 4096 key 合并队列静默淘汰
P2：C 扫全量 paint、B 扫动态 rebuild 造成 GUI 长尾
P3：缓存线程锁竞争、QStorageInfo 查询、磁盘写入和 flush
P4：小车/纠偏/相机线程与超声共享进程调度资源
P5：双窗口失活触发纠偏停止，属于现有行为，不等于扫描线程崩溃

确认方法：
- 如果 CScan FIFO 丢弃数大于 0：问题在采集/解码余量。
- 如果 CScan FIFO 丢弃数为 0，但 UI pending 丢弃数大于 0：问题在 GUI 合并/绘制。
- 如果 paint P99 很大且页面切换后 drain 延迟：优先修 CScanWidget。
- 如果 cache enqueue 等待很大：优先拆 DirectConnection 和缓存锁。
- 如果 CPU 平均不高但线程周期抖动大：是调度/阻塞问题，不是纯算力不足。


六、优化原则
======================================================================
1. 先测量，再改结构。
2. 显示链路允许 latest-value 覆盖；B/C 扫描链路不允许静默丢包。
3. 控制面和数据面分离。
4. SDK 回调只做最小入队，不做日志、磁盘、UI 或复杂解析。
5. 所有队列必须有上限、丢弃原因、丢弃数量和丢失范围。
6. 先做进程内解耦，再做进程外隔离。
7. 不用“增加大量线程”代替数据通路优化。
8. 不改变 UI、参数范围、PRF 限幅、远程协议、文件格式和安全行为。

8.2 CScan 按字节限流
文件：D:\dev\deskCrawlingRobot\CrawlingRobotSV\PA1664WorkbenchTmp\src\devicecontroller.h
位置：106-115
删除仅按包数的容量判断，新增：
- maxQueueBytes
- maxQueueAgeMs
- packetBytes
- queueBytes
- overflow reason

单包大小公式（来自 PacketDecoder::validatePacket）：
bytes = (groupOffsetWords + beamCount * (pointCount + 16)) * 2 + 32

估算：
- pointCount=1024、beamCount=1、offset=0：约 2112 字节/包。
- 8 kHz 时：约 16.9 MB/s。
- 1024 包：约 2.1 MB、约 128 ms。

十三、小车是否能获得更多计算资源
======================================================================
答案：可以获得更稳定的资源，但不是增加物理 CPU 核数。

独立超声进程的收益：
- 把 SDK 回调、解码、缓存、录制移出主进程；
- 页面切换不再直接占用超声处理；
- 超声服务崩溃不拖垮小车控制；
- 可以让主进程运动/纠偏线程获得更稳定的调度；
- 可以给缓存/日志线程更低优先级。

但独立进程也有成本：
- IPC 延迟和协议复杂度；
- 共享内存生命周期；
- 服务启动和恢复；
- 日志和配置路径；
- 跨进程错误处理；
- 需要严格的序列号、ack 和回滚。

小车控制不建议第一阶段拆成独立进程。原因是安全关键路径需要额外设计急停、watchdog、反馈丢失、命令超时和进程崩溃恢复。优先做超声隔离和进程内线程优化即可。
