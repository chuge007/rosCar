# 原 ROS 系统梳理与迁移边界

## 原系统运行链路

`crawling_robot_bringup/launch/robot.launch.py` 会启动下列节点：

| 范围 | 原节点 | 作用 | 本次处理 |
| --- | --- | --- | --- |
| 底盘 | `base_drive_node` | `/cmd_vel` 转左右轮速度、限速与斜坡、封装 V3.8 电机命令 | 已迁移并重新设计 |
| MWD RS485 | `WheelMotorController` | 单总线轮电机命令、状态查询和反馈解析 | 已迁移并重新设计 |
| IMU | `rim302_imu_node` | RIM302 串口解析为 IMU 数据 | 已迁移为独立 Qt 设备线程与中文监视界面 |
| 外部编码器 | `modbus_encoder_node` + `encoder_odom_node` | Modbus 编码器读数和里程计 | 主界面“车体状态”保留未接入状态；未迁移，不参与双驱动轮同步闭环 |
| 扫描/夹具轴 | `canopen_axis_node` | CANopen 线性轴、归零和状态轮询 | 可检测 CANopen 节点并在“车体状态”显示；实时反馈和控制暂缓 |
| 激光 | `mv3dlp_laser_node` | 海康 3D 线激光采集 | 已迁移为独立 Qt 设备线程、点云转换与可选坐标平面预览窗口 |
| 自动纠偏 | `laser_path_follower_node` | 点云+里程计生成 `/cmd_vel` | 已改为原始图像断口双边缘采样、轮端里程分段拟合与角度跟踪 |
| 监控 | `crawling_robot_monitor` | ROS/Tk 监控界面 | 被原生 Qt 状态与诊断界面替代底盘部分 |

原数据流为：

```text
手动控制或原图双边缘分段纠偏 -> 线速度/角速度 -> SynchronizedDriveController
  -> WheelMotorController -> RS485 总线 -> 两台 MWD 驱动电机
                                      <- 状态 2 反馈 / 编码器
```

## 双轮不同步的根因

原节点已经有正确的几何换算、统一限速和同向差速约束，但电机回传只用于发布 `JointState` 和日志。控制输出未基于左右轮实际速度作任何校正，也没有要求两路反馈都正常才允许运动。

同时，ROS CAN 桥按单帧维护发送队列。即使它会合并同一电机的旧速度帧，左、右命令仍是两条独立队列项，而不是“同一控制周期的一对命令”。负载变化、总线短暂延迟或一侧反馈丢失时，系统无法保证两侧前进量一致。

## 新桌面架构

`CrawlingRobotDesktop.exe` 不使用 ROS/DDS。控制计算以 20 ms 周期运行，正常电机通信按 334 ms 周期限频：

```text
Qt 输入 -> 加速度矢量斜坡 -> 差速混控 -> 电机指令上限 -> 响应自适应同步 -> 左右 MWD RS485 帧
                                                                ^
                                                     左右电机新鲜反馈均必须有效
```

- 平移差速转弯时，按配置保持内轮/外轮最小比值，避免内侧物理轮倒转。
- 单独按左/右为零线速度原地转向；与前进或后退组合时才形成平移圆弧。
- 轮速上限采用整体缩放，并同时受 `4300 dps` 成对运动上限约束（当前 100:1 传动约为 `0.030 m/s`）。该值低于实测慢侧约 `4350 dps` 的内部上限，使短时点动从第一帧起就在两侧共同可达到的速度区间内；反馈自适应只负责修正剩余差异。
- 行驶时 `0xA2` 的回复直接提供状态 2 反馈，不再额外发送 `0x9C`；静止时才以约 3 Hz 发送 `0x9C` 保活。
- 同步器用实际轮速除以上一次真正下发的轮速，滤波学习左右电机的响应系数；同向行驶时保留较慢侧命令，只降低较快侧，并按预测物理轮速维持直行或平移转弯比例。原地转向和极低速不参与该补偿，任何补偿都不会改变轮子方向。
- 左右回传分别更新时间戳；800 ms 反馈窗口允许 3 Hz 通信偶发丢失一帧，任一路持续过期仍会故障停机。
- 连接、零速、点动松开、自动纠偏停止、禁用、急停、故障和断开都先用 MWD `0x81` 停止两侧电机，再用 `0x92` 读取各自当前多圈角度，并用带限速的 `0xA4` 保持该位置。只在进入静止时发送这组命令，保持成功后不周期重发；失败才按 334 ms 周期重试。
- 轮子控制路径有意不使用 `0x8C`，因为实机没有已验证的机械抱闸。`0xA4` 只提供通电位置保持，断电会释放；非零 `0xA2` 速度命令可以直接切回速度环并重新起动。

## 暂缓的 CANopen 轴

`canopen_axis_node` 默认配置为 `dry_run: true`、`protocol_verified: false`，轴行程、速度、加速度、每米脉冲数也全为 0。这表示该功能在现有工程中并没有可安全迁移的现场参数或已验证协议；将它直接做进新界面会造成“界面看起来可用、实机却不可预测”的风险。

迁移它之前需要给出每个轴的已验证 CANopen 对象字典、节点 ID、软限位、单位换算和归零传感器语义。届时应把它加为独立的 `AxisController`，不能与底盘成对轮控共用状态机或安全限位。

## IMU、线激光与日志

- RIM302 经独立串口在 115200 bps 下接入，连续帧经 CRC 校验后显示横滚、俯仰、航向、三轴陀螺仪和三轴加速度。
- MV3DLP 通过随程序发布的 Windows x64 SDK 扫描、连接和采集。原始 JPEG 图像用于界面预览和激光线断口检测；检测器定位左右激光段之间的最大有效断口，并按配置的“激光横向范围”把两侧边缘像素映射为横向坐标。自动纠偏首次同步直行一段并按轮端编码器距离采样，停稳后原路退回起点，对两侧点列分别做带离群点剔除的直线拟合，以平均斜率计算路径偏移角。随后底盘按编码器航向闭环前进，每到一个分段边界用新采集的双边缘点更新拟合角并继续微调。每个直线段的逐帧断口数据由独立写图线程绘制为一张 PNG，叠加激光段、缺口左右边缘、左右拟合线和中心线，保存到 `laser_trajectory_maps/<会话时间>/segment_XXXX.png`，图像编码不会阻塞底盘控制线程。图像、有效断口或轮端反馈超时会停止纠偏；点云模式仍保留限量预览能力。
- “车体状态”使用双列监视布局：左列显示车体运动和辅助设备，右列显示驱动轮编码器/电机与 IMU，避免将车体实时数据分散到配置页。
- 操作入口、模块调用、状态切换、连接配置、通信故障及恢复事件写入程序旁 `logs/robot_console.log`。日志按 `INFO/WARN/ERROR` 和模块分类；相机帧、IMU 样本及底盘周期命令等高频正常数据不重复落盘，相机停止时仅写一条采集汇总。该文件最多 2 MiB，达到上限后仅保留最新约 1.5 MiB 的完整日志行。
