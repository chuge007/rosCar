## 产品概述

一份给第三方软件开发者的《小车端功能接口手册》。读者没有任何本项目背景，只会问一件事：我要做某件事，往哪个地址发、发什么字节、能收到什么。手册必须让他在不读源码、不问人的前提下，独立写出可运行的客户端。

## 核心功能

- **一个功能一条，条目自包含**：每条固定给出「能不能用接口做、实现方式、IP、端口、指令、完整报文、前置、返回/回传、失败表现」，单看这一条即可发出正确请求。
- **二进制报文逐字节说明**：凡不是 JSON 的通道，必须给出字段偏移表（偏移、类型、字节数、取值、单位）、一段十六进制示例、以及构造步骤（含签名密钥来源与计算方法），不允许出现“直接发实时包”这类内部省略语。
- **覆盖整个软件的全部功能与设置**：运动控制、底盘全部配置项、夹爪与探头间距全部配置项、超声全部可调参数、超声设备与预设功能、IMU/激光/双路相机/自动纠偏、九类数据回传；对上位机本地功能（录制回放、扫描会话、屏幕布局、远程桌面、本地日志）明确标注“无对外接口”。
- **前置零上下文扫盲**：术语表、四条通道的分工与原因、握手流程图与 sessionToken 用途、JSON 请求与二进制报文两种形态的对照图、功能×通道能力矩阵。
- **样例可直接复现**：每组给出完整可复制的 JSON 或字节序列，数值标注单位与范围，并说明如何确认成功。

## 阅读效果

标题即功能名，地址与端口是每条前两行；同类参数在组首说明一次统一入口，条目内只保留该方法名、参数顺序与报文片段；全篇不出现未定义术语，不要求读者跨章拼装字段。

## 技术栈与交付形态

- 交付物为 Markdown 文档，不修改任何 C++ 代码、构建脚本与配置。
- 事实来源全部取自现有实现：`src/common/protocol/*`（帧格式与常量）、`src/backend/*_host_service.cpp`（operation 与字段）、`src/backend/ultrasound_parameter_rpc.cpp`（参数名与参数个数）、`src/robot/drive_settings.cpp` 的 `DriveSettings::save()`（底盘 INI 键）。
- 文档分两处：新建功能手册承载全部功能细节；旧协议文档保留 1-14 章线格式说明，附录 A 的压缩表删除后改为索引页指向手册，避免两份文档重复描述同一事实。

## 实施策略

1. **先盘点、后写作**。从 UI 与后台服务两侧枚举“用户可操作项”，产出一张「功能 → 是否可接口化 → 通道 → operation/报文」矩阵。矩阵是写作清单，也是最后的验收清单，避免漏项。
2. **先定模板、再填内容**。三类模板固定：动作类（有请求响应）、参数类（配置项）、回传类（数据流）。模板不允许在执行中随意变形。
3. **二进制条目按“可构造”标准写**：字段偏移表 + 十六进制样例 + 签名步骤。样例必须与字段表逐字节对得上（长度、序号的字节数都要核）。
4. **内部术语清零**：出现“实时包”“直接发”“按协议”等词即视为缺陷；每个名词首次出现必须在术语表有定义。

## 事实基准（写作时不得改写）

- 端口：控制 TCP 43100、实时 UDP 43101、媒体 UDP 43102、批量 TCP 43103，默认监听 0.0.0.0，小车默认地址 192.168.1.20。
- 控制帧 50 字节，magic 0x50413136、version 1、type 1..8、payload 为 compact JSON、末尾 CRC32。
- 实时帧 44 字节 + 16 字节 HMAC，type 1..5，运动设定值 50 ms 一帧、租约 200 ms。
- 媒体帧 58 字节 + 16 字节 HMAC，单报不超过 1472 字节，每片载荷不超过 1398 字节，组装超时 1500 ms。
- 批量帧 28 字节 + 16 字节 HMAC，单帧不超过 32 MiB。
- HMAC 统一为：对“头+载荷”整段用 32 字节会话密钥做 HMAC-SHA256，取前 16 字节。
- 数据帧 magic 为 PAD1，type 1..6，其中 1/2/4/5 经 qCompress（前 4 字节为大端原始长度），3 为 JPEG，6 不压缩。
- 超声写 `ultrasound.parameters.apply`、读 `ultrasound.parameters.getMany`；参数个数不符时错误文本为“参数个数错误：期望 N，收到 M”。
- 底盘设置为 `{"schema":13,"iniBase64":"整份 INI 的 base64"}`，键位于 `[drive]` 组。
- 单操作台独占：第二个连接收到 host.busy 后 250 ms 被断开，且拿不到 UDP 密钥。

## 条目模板（全书统一）

```text
### 功能名（用户视角叫法）
- 能不能用接口做：可以 / 不可以（仅上位机本地功能）
- 实现方式：JSON 请求 / 二进制报文 / 事件订阅 / 数据流订阅 / 无接口
- IP：192.168.1.20（小车地址）
- 端口：TCP 43100 / UDP 43101 / UDP 43102 / TCP 43103
- 指令：operation 字符串，写明它是 JSON 的哪个字段；
        或报文名 + type 值，写明这是二进制、没有 operation 字段、靠哪个字段识别
- 报文：JSON 给完整对象；二进制给字段偏移表 + 十六进制示例 + 构造步骤（含签名）
- 前置：必须先完成什么，要等哪个事件
- 返回 / 回传：响应字段或数据流，如何确认成功
- 失败表现：错误码 / 无反应时查什么 / 超时行为
```

## 二进制条目示例（写作基准）

「前进」条目必须写成：UDP 43101、44 字节头加 16 字节签名共 60 字节、靠头内 type=2 识别、给出 0..43 字节逐字段表（含 ttlMs=200、linearMilliMps=80、angularMilliRadps=0）、给出十六进制样例、说明签名用握手回包 sessionToken 的 base64 解码后 32 字节计算，而不是只写“发实时包”。

## 实施要点

- 参数条目不重复“如何下发”的完整流程，只在每组开头写一次统一入口；条目内保留方法名、参数顺序、单位与完整报文片段。
- 二进制布局一律用四列表（偏移/类型/长度/含义），禁止纯文字描述。
- 所有示例数值标注单位与取值范围，避免按错单位下发。
- 文档体量较大时用锚点与组内目录控制导航，不拆散事实来源。
- 完成前做反向核对：从代码抽取 operation 字符串与常量清单，与手册条目逐条比对，缺失或多写的列入差异清单并修正。
- 不改动 `src/`、构建脚本、配置；不影响 Workbench 与 Host 两个构建目标。

## Agent Extensions

### SubAgent

- **code-explorer**
- Purpose: 盘点整个软件的全部可操作功能与设置项（UI 面板项、菜单项、服务分支），产出「功能 → 是否可接口化 → 通道 → operation/报文」矩阵；并在收尾阶段从代码反向抽取 operation 与常量清单，与手册逐条比对。
- Expected outcome: 一份无漏项的功能清单与一份差异清单，确保手册覆盖所有功能且与代码一致。
