## Product Overview

小车操作台持续显示两路摄像头实时画面，底盘前进/后退时左右轮同步转动，主机与操作端保持单会话控制，异常时能从记录定位到具体环节。

## Core Features

- 两路摄像头画面连续刷新，不再停滞或长时间延迟；既有传感器数据保持正常。
- 相机帧从采集、确认、编码、发送到接收的每一段有可核对记录；无画面时能定位断点。
- 前进/后退时左轮与右轮按目标速度转动，不再表现为左转；速度指令、反馈速度和角度变化可验证。
- 主机启动后保持运行，双操作端不再抢会话；配置以小车实际设备为准。
- 执行过程按计划连续完成，仅在需要现场点前进或桌面启动时提示。

## Tech Stack Selection

- 语言与框架：C++17，Qt 6.8.3/5.15.2，qmake 加 MSVC 2022，Qt 信号槽、QThread、QTimer、QImage、QUdpSocket、QSerialPort。
- 相机与媒体：OpenCV/FFmpeg RTSP 读取，QImage/JPEG 编码，现有 `kMediaStreamUsbCameraBase`、`MediaStreamKind::UsbCameraImage`、`MediaServer`、`MediaClient`。
- 驱动轮：SLCAN 串口、ServoProtocol CAN 帧、现有 `0xA2/0xF3/0x88/0x8C/0x81` 指令链。
- 诊断与部署：`crawling::AppLogger` 分类日志，现有 `MEDIA.TX`、`媒体接收(5s)`、`DRIVE.CAN`；Windows WER/cdb 转储；PowerShell、SSH/scp；根目录 `compile_commands.json` 与 clangd。
- 约束：全部为现有 C++ 项目；本地源码修改仅限工作区 `d:/dev/deskCrawlingRobot/CrawlingRobotSV/PA1664WorkbenchTmpSeparate`；远端仅按用户已授权部署目录查看记录和替换 exe；更新 exe 前必须使用 clangd + compile_commands。

## Implementation Approach

### 相机链路

先用调用链分析确认断点，再修复现有 mailbox 背压链路，不引入新架构。已核实 `NetworkStreamReader::run` 在 `emit frameReady` 前把 `busy_` 置 1，`NetworkStreamReader::releaseFrame` 才清零；`RobotUsbCameraController::frameConsumed` 会调用 `releaseFrame`。`RobotPeripheralHostService` 的 `frameChanged` lambda 在拒绝分支调用了 `frameConsumed`，但接收分支只把 `submitUsbImage` 投递给 `RobotPeripheralMediaEncoder`，没有确认帧，导致 `busy_` 可长期停留 1，后续相机帧不再进入编码器；这与 `usb0=0 usb1=0` 而点云/IMU 正常的现象一致。

修复策略：在 `frameChanged` 接收分支投递 `submitUsbImage` 后，无论编码器是否暂时丢弃，都按现有 `QMetaObject::invokeMethod` 方式回投 `frameConsumed`；保留 `ownerSessionId_`、`mediaReceptionActive_`、`encoder_` 门控和 `kUsbImageIntervalMs` 限流；用每 2 秒聚合的分段计数确认 `frameReady`、`frameChanged`、`submitUsbImage`、`frameConsumed`、`mediaReady`、`MEDIA.TX`、操作端接收是否逐级增长。激光灰度图按现有设计不再上传，`laser_img=0` 不作为回归项；仅恢复两路 `0x0300/0x0301` 相机画面。

### 左轮链路

不再盲目增加未知协议动作。基于已稳定的主机，在 `WheelMotorController::sendSpeed` 与 `pollCanFeedback` 补齐可验证证据：记录首帧和帧类型切换时的真实 CAN 数据，确认 `0xA2` 到 `0xF3` 是否真正下发；保留 3 次 `0x88 + 0x8C` 恢复尝试和 1.2 秒停滞判定。点前进后，以 `left_9c` 角度变化、反馈速度、`left_motor_feedback_raw_dps`、`can_left_legacy_speed`、`can_left_recover` 判定结果；若 `0xF3` 与恢复尝试后仍不动，输出硬件判定结论并停止自动试探，避免未知 `0xA4` 造成非预期动作。

### 性能与可靠性

- 每帧只做常数级计数与一次 `QImage` 拷贝；分段日志按 2 秒窗口聚合，不逐帧打印，复杂度为常数级；传输分片数和 `kMaxMediaFragments` 不变。
- 瓶颈仍是 100 Mbps 网卡与 JPEG 编码；保持现有 `kUsbImageIntervalMs`、`kLaserPointIntervalMs`、`kImuIntervalMs`，不提升推流频率。
- 所有帧确认必须覆盖正常、空图、无会话、无订阅、编码器未激活、旧 generation、停止、异常断开等分支，避免相机线程死锁或看门狗误重连。
- 保留 `GuardedThread`、`UltrasoundHostService::dispatchRequest` 异常护栏和 `main.cpp` 残留锁复核，避免主机再次 abort 或双击秒退。
- 右轮、超声、夹子、点云、IMU 路径不改行为；不新增网络协议、不新增界面、不做无关重构。

## Architecture Design

### 系统结构与数据流

相机帧链路沿用现有分层：读取线程只产出最新帧，外设服务做会话门控和帧确认，媒体编码线程做 mailbox 覆盖式编码，主机发送侧记录 `MEDIA.TX`，操作端接收侧记录 `媒体接收(5s)`。本次只补确认回环和分段计数，不改线程模型和协议。

```mermaid
flowchart LR
  R[NetworkStreamReader]
  C[RobotUsbCameraController]
  P[RobotPeripheralHostService]
  E[RobotPeripheralMediaEncoder]
  H[HostApplication MEDIA.TX]
  S[MediaServer]
  O[MediaClient]
  U[RobotControlPanel]
  R -->|frameReady| C
  C -->|frameChanged| P
  P -->|submitUsbImage| E
  E -->|mediaReady| H
  H -->|sendMessage| S
  S -->|UDP fragments| O
  O -->|messageReceived| U
  P -.->|frameConsumed| C
  C -.->|releaseFrame| R
```

左轮链路保持现有 `WheelMotorController` 到 `ServoProtocol` 的单向控制结构：速度帧构造、一次运行帧日志、停滞检测、0xF3 降级、有限次数恢复、2 秒 CAN 统计。所有新增日志按状态变化或窗口输出，不进入每帧热路径。

## Key Code Structures

```cpp
struct CameraPipelineCounters {
  quint64 frameReady = 0;
  quint64 frameChanged = 0;
  quint64 submitted = 0;
  quint64 acknowledged = 0;
  quint64 droppedNoConsumer = 0;
};

void RobotUsbCameraController::frameConsumed(int slot);
void NetworkStreamReader::releaseFrame();
void RobotPeripheralMediaEncoder::submitUsbImage(int slot, const QImage&amp; image);
```

上述接口保持现有线程亲和性：`frameReady` 到 `frameChanged`、`submitUsbImage` 到 `mediaReady` 继续使用 `Qt::QueuedConnection`；`frameConsumed` 必须回到 `RobotUsbCameraController` 线程后调用 `releaseFrame`，不得跨线程直接改 `busy_`。

## Agent Extensions

### Skill

- **gitnexus-debugging**
- Purpose: 跟踪 `NetworkStreamReader::frameReady`、`RobotUsbCameraController::frameChanged`、`RobotPeripheralHostService::submitUsbImage`、`MediaServer::sendMessage` 和 `MediaClient::processDatagrams` 的执行流，定位相机帧停滞断点。
- Expected outcome: 输出可核对的调用链和每层计数预期，证明断点是否在帧确认、编码器激活、媒体发送或接收组装。
- **lsp-code-analysis**
- Purpose: 核对 `frameConsumed`、`releaseFrame`、`mediaReceptionActive`、`submitUsbImage`、`mediaReady`、`leftSpeedLegacy_` 的定义、引用和调用层级。
- Expected outcome: 形成精确符号清单，避免误改同名函数、旧 generation 回调或 RS485 分支。
- **gitnexus-impact-analysis**
- Purpose: 在修改 `RobotPeripheralHostService`、`RobotUsbCameraController`、`NetworkStreamReader`、`RobotPeripheralMediaEncoder`、`WheelMotorController` 前评估上游调用者、执行流和风险级别。
- Expected outcome: 给出 blast radius；若为 HIGH/CRITICAL 先报告再修改；确认改动不影响点云、IMU、超声、夹子、右轮路径。

### SubAgent

- **code-explorer**
- Purpose: 以 medium 到 very thorough 程度跨目录检索相机帧确认、媒体订阅、日志计数、驱动轮降级和部署脚本的现有约定。
- Expected outcome: 汇总所有修改点与验证点，确保目录结构完整、无遗漏调用点、符合项目现有模式。
