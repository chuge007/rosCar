# 0. 十分钟上手

## 0.1 你只需要做三件事

1. **连 TCP `43100` 握手**，拿到两个东西：`sessionId`（一个数字）和 `sessionToken`（32 字节密钥的 Base64）。
2. **发 JSON 请求**：所有"设置参数、连接设备、使能、查状态"都是往 TCP 43100 发一段 `{operation, data}`，靠 `sessionId` 认身份。
3. **发 UDP 二进制报文**：所有"让车动、收图像"走 UDP，靠 `sessionToken` 算签名。

没有任何 HTTP 接口，也不是文本命令行。控制通道是"50 字节二进制头 + 一段 JSON"，数据通道是"固定字段的二进制包"。

## 0.2 四条通道分别管什么

| 通道 | 协议 | 端口 | 上面跑什么 | 你需要它吗 |
|---|---|---|---|---|
| 控制 | TCP | **43100** | JSON 请求/响应、事件通知 | **必须**，没有它拿不到密钥 |
| 实时 | UDP | **43101** | 小车速度指令、急停、轮速遥测 | 要开车就必须 |
| 媒体 | UDP | **43102** | 超声图像、激光点云、相机、IMU | 要看画面/点云才需要 |
| 批量 | TCP | **43103** | 整包扫查批次（可靠、不丢） | 要完整扫查数据才需要 |

## 0.3 为什么"让车动"不走 TCP

这是一个常见误解，先说清楚：

- TCP 43100 是**请求-响应**：你发一条，主机回一条。适合"把增益设成 35 dB"这种一次性动作。
- 小车行驶需要**每 50 ms 一个速度值**，而且"晚到的旧速度"必须被丢弃。用 TCP 会因为重传把旧速度补上来，反而危险。
- 所以速度指令走 **UDP 43101**，每帧自带有效期 `ttlMs`。主机 200 ms 收不到新帧就自动停车。

**结论**：想开车，必须实现 UDP 43101。只做 TCP 的客户端能设参数、能读状态，但车不会动。

## 0.4 术语表

| 名词 | 含义 |
|---|---|
| 小车 / 主机 / Host | 运行 `PA1664RobotHost.exe` 的那台工控机，直连所有硬件 |
| 上位机 / 客户端 | 你写的程序 |
| 帧（frame） | 一次传输的最小单位：一段固定格式的字节 |
| 头（header） | 帧开头的固定长度字段区，描述这帧是什么、多长 |
| 载荷（payload） | 头后面的实际内容 |
| operation | JSON 请求里的字符串字段，说明"要主机做什么"，例如 `robot.enable` |
| 会话（session） | 一次握手建立的连接身份，用 `sessionId` 标识 |
| sessionId | 主机分配的会话号，后续每个 TCP 帧都要带 |
| sessionToken | 主机分配的 32 字节密钥（Base64 文本），用于给 UDP 帧签名 |
| HMAC | 一种带密钥的签名算法。这里统一是 HMAC-SHA256，取前 16 字节 |
| 分片（fragment） | 一条大消息拆成多个 UDP 包发送，每包带序号 |
| 租约（lease） | 运动指令的有效期，过期即停车 |
| groupId | 超声的"工作组"编号，多组探头/多闸门时区分用；`-1` 表示当前组 |
| 预设（preset） | 一整套超声参数的存档，可命名、切换、导入导出 |
| 楔块（wedge） | 探头前的斜块，影响声束折射角度 |
| Gate A/B/C/I | 超声闸门，用来在 A 扫波形上取测量点 |
| PRF | 采集帧率（每秒发射次数），过高会有安全风险，主机会限幅 |
| PCS | 相控阵聚焦的焦点间距，由楔块角度和深度算出（本机计算，不下发） |

# 1. 建立会话（必读）

## 1.1 握手流程

```
你的程序                                小车 (192.168.1.20)
   |  TCP connect :43100                     |
   |----------------------------------------->|
   |  Hello  (type=1, sessionId=0)            |
   |----------------------------------------->|
   |                                          | 分配 sessionId + 32字节密钥
   |  HelloAck (type=2, 含 sessionId/token)   |
   |<-----------------------------------------|
   |  Event: host.ready                       |
   |<-----------------------------------------|
   |  Request (operation=...)                 |
   |----------------------------------------->|
   |  Response {ok, data}                     |
   |<-----------------------------------------|
   |  Ping (每 250 ms)                        |
   |----------------------------------------->|
```

握手成功后 **立刻** 会收到 `host.ready` 事件。如果先收到的是 `host.busy`，说明已有别的程序在控制这台车，你会在 250 ms 后被断开。

## 1.2 控制帧格式（50 字节头，小端）

| 偏移 | 长度 | 字段 | 类型 | 填什么 |
|---|---|---|---|---|
| 0 | 4 | magic | u32 | 固定 `0x50413136`，字节序列是 `36 41 31 50` |
| 4 | 2 | version | u16 | `1` |
| 6 | 2 | type | u16 | 见 1.3 |
| 8 | 2 | flags | u16 | 一般 0；响应帧是 1 |
| 10 | 8 | sessionId | u64 | 握手前填 0，之后填 ack 里的值 |
| 18 | 8 | sequence | u64 | 每帧 +1，从 1 开始，**必须严格递增** |
| 26 | 8 | requestId | u64 | 自己维护的请求号，响应会带回同一个值 |
| 34 | 8 | timestampUs | u64 | 当前微秒时间戳，可填 0 |
| 42 | 4 | payloadLen | u32 | JSON 字节数，最大 1 MiB |
| 46 | 4 | crc32 | u32 | 对 payload 算 CRC32 |
| 50 | N | payload | bytes | compact JSON，如 `{"operation":"robot.enable","data":{"enabled":true}}` |

**CRC32 算法**（与 zlib 相同）：多项式 `0xEDB88320`，初值 `0xFFFFFFFF`，结果按位取反。C++ 可用 `zlib` 的 `crc32()`，Python 用 `zlib.crc32()`。

> 注意：只有 payload 参与 CRC，头本身不校验。会话安全靠 `sessionId` 校验和 UDP 的 HMAC。

## 1.3 帧类型

| type | 名称 | 方向 | 用途 |
|---|---|---|---|
| 1 | Hello | 你 → 车 | 握手请求 |
| 2 | HelloAck | 车 → 你 | 握手应答 |
| 3 | Request | 你 → 车 | 业务请求，payload 是 `{operation,data}` |
| 4 | Response | 车 → 你 | 业务应答，payload 是 `{ok,data}` |
| 5 | Event | 车 → 你 | 主动通知，payload 含 `event` 字段 |
| 6 | Ping | 你 → 车 | 心跳 |
| 7 | Pong | 车 → 你 | 心跳应答 |
| 8 | Error | 车 → 你 | 协议级错误 |

## 1.4 Hello 报文

payload：

```json
{"protocolVersion":1,"clientId":"OtherApp","clientName":"第三方软件","capabilities":["control.v1"]}
```

完整 50 字节头示例（payload 长度按上面 JSON 实际字节数填，CRC 自算）：

```
36 41 31 50              magic
01 00                    version = 1
01 00                    type = 1 (Hello)
00 00                    flags = 0
00 00 00 00 00 00 00 00  sessionId = 0（握手前必须为 0）
01 00 00 00 00 00 00 00  sequence = 1
01 00 00 00 00 00 00 00  requestId = 1
xx xx xx xx xx xx xx xx  timestampUs
6c 00 00 00              payloadLen = 108（按实际 JSON 长度）
xx xx xx xx              crc32（按上面算法算）
{...JSON...}
```

## 1.5 HelloAck 字段

```json
{"sessionId":"7","sessionToken":"<base64 32字节>","protocolVersion":1,
 "realtimePort":43101,"mediaPort":43102,"bulkPort":43103,
 "heartbeatIntervalMs":250,"motionSendIntervalMs":50,"motionLeaseMs":200,
 "capabilities":["robot.control.v1","robot.telemetry.v1","robot.settings.v1",
                 "robot.sensors.v1","robot.media.v1",
                 "ultrasound.control.v1","ultrasound.parameters.v1",
                 "ultrasound.media.v1","ultrasound.bulk.v1"],
 "hostName":"DESKTOP-XXXX"}
```

| 字段 | 怎么用 |
|---|---|
| `sessionId` | 字符串形式的数字，转成整数填到每个 TCP 帧的 offset 10 |
| `sessionToken` | Base64 解码得到 32 字节，用于 UDP 签名 |
| `realtimePort` 等 | 实际端口，**不要写死**，以这里为准 |
| `heartbeatIntervalMs` | 你发 Ping 的间隔 |
| `motionLeaseMs` | 运动帧有效期，填进 UDP 头的 `ttlMs` |

## 1.6 心跳与断链

| 规则 | 值 | 后果 |
|---|---|---|
| 发 Ping 间隔 | 250 ms | 不发则 2 s 后被断开 |
| 握手没有 Hello | 5 s | 主机断开 |
| 帧 sequence 回退 | 立即 | 主机断开 |
| 请求超时 | 5 s | 主机不再回这一条，按失败处理 |
| 链路空闲 | 1 s 无任何入站帧 | 客户端会判链路异常并重连 |
| 未决请求上限 | 2048 | 超了会被拒 |

Ping 的 payload 可以带 `{"clientTimeMs":"..."}`，也可以为空对象。

## 1.7 两种报文形态

这套接口只有两种报文，理解这一点很关键：

**形态一：JSON 请求（TCP 43100）**

```
[50字节头] + {"operation":"robot.enable","data":{"enabled":true}}
             ^^^^^^^^^^^^ 靠这个字符串决定做什么
```

**形态二：二进制报文（UDP 43101 / 43102，TCP 43103）**

```
[44字节头(含type=2)] + [0字节载荷] + [16字节签名]
                      ^^^^^^^^^^ 没有 JSON，没有 operation
                      靠头里第 6 字节 type=2 表示"这是运动指令"
```

本章后面凡是写"没有 operation"的地方，都是形态二，会给出完整的逐字节表。

# 2. 小车运动

## 2.0 前置：任何运动都必须先做这三步

```
第1步  TCP 43100  robot.connect        → 等事件 robot.connectionChanged{connected:true}
第2步  TCP 43100  robot.enable         → 等事件 robot.stateChanged{stateKey:"enabled"}
第3步  UDP 43101  每 50 ms 发运动帧
```

少任何一步，车都不会动，而且**没有任何报错**（因为 UDP 没有响应）。这是最常见的"发了没反应"原因。

## 2.1 运动报文（MotionSetpoint）逐字节

- 通道：UDP，目标 `192.168.1.20:43101`
- 总长度：44 字节头 + 0 字节载荷 + 16 字节签名 = **60 字节**
- 单报上限：**1200 字节**（运动帧只有 60 字节，远小于上限，不用分片）
- 没有 JSON，没有 operation，主机靠头里 `type=2` 识别

| 偏移 | 长度 | 字段 | 类型 | 本指令填什么 |
|---|---|---|---|---|
| 0 | 4 | magic | u32 | `0x50413136`，字节 `36 41 31 50` |
| 4 | 2 | version | u16 | `1` |
| 6 | 1 | type | u8 | **`2`**（MotionSetpoint） |
| 7 | 1 | flags | u8 | `1`（表示带签名） |
| 8 | 8 | sessionId | u64 | 握手拿到的会话号 |
| 16 | 8 | sequence | u64 | 每帧 +1 |
| 24 | 8 | timestampUs | u64 | 当前微秒 |
| 32 | 2 | ttlMs | u16 | **`200`**（有效期，50..1000） |
| 34 | 4 | linearMilliMps | i32 | 线速度，m/s × 1000 |
| 38 | 4 | angularMilliRadps | i32 | 角速度，rad/s × 1000 |
| 42 | 2 | payloadLen | u16 | `0` |
| 44 | 16 | 签名 | bytes | HMAC-SHA256(前 44 字节, 密钥) 取前 16 字节 |

**签名怎么做**：

```
key = base64_decode(sessionToken)        // 32 字节
tag = HMAC-SHA256(key, 头44字节)[0..15]  // 取前 16 字节
发送 头44字节 + tag
```

**前进 0.08 m/s 的完整示例**（sessionId=7、sequence=42、timestamp 任意）：

```
36 41 31 50                                    magic
01 00                                          version
02                                             type = MotionSetpoint
01                                             flags = 签名存在
07 00 00 00 00 00 00 00                        sessionId = 7
2a 00 00 00 00 00 00 00                        sequence = 42
34 12 0f 6b 18 00 00 00                        timestampUs
c8 00                                          ttlMs = 200
50 00 00 00                                    linear = 80  → 0.080 m/s
00 00 00 00                                    angular = 0
00 00                                          payloadLen = 0
<16 字节签名>
```

## 2.2 前进 / 后退 / 转向

| 功能 | linearMilliMps | angularMilliRadps | 说明 |
|---|---|---|---|
| 前进 | `+80` | `0` | 0.08 m/s |
| 后退 | `-80` | `0` | |
| 前进左转 | `+60` | `+300` | 0.06 m/s + 0.3 rad/s |
| 前进右转 | `+60` | `-300` | |
| 原地左转 | `0` | `+400` | 只转不走 |
| 原地右转 | `0` | `-400` | |
| 停车 | `0` | `0` | 发一帧即可，车立即停 |

- 线速度上限由车上配置决定，默认 `0.120 m/s` → `linearMilliMps` 最大 120。
- 角速度上限默认 `0.873 rad/s` → `angularMilliRadps` 最大 873。
- 超限不会报错，主机会自动截断到上限。

**条目：前进**

- 能不能用接口做：可以
- 实现方式：二进制报文
- IP：192.168.1.20
- 端口：UDP 43101
- 指令：没有 operation。这是一段 60 字节的二进制报文，靠头里第 6 字节 `type=2` 识别
- 报文：见 2.1 的字段表与示例；`linearMilliMps=80, angularMilliRadps=0, ttlMs=200`
- 前置：`robot.connect` 成功 → `robot.enable` 成功
- 返回：无响应。发完看 UDP 43101 的遥测，`appliedLinearMps` 接近 0.08 说明生效
- 失败表现：停发 200 ms 自动停；未使能则 `appliedLinearMps` 恒为 0；签名错则包被丢弃

## 2.3 停车与急停

**条目：停车**

- 实现方式：二进制报文 + JSON 确认
- 端口：UDP 43101（主）+ TCP 43100（确认）
- 指令：先发一帧 `linearMilliMps=0, angularMilliRadps=0` 的 MotionSetpoint；再发 operation `robot.motion.stop`
- 报文：`{"operation":"robot.motion.stop"}`，data 可省略
- 返回：`{"ok":true}`，并收到事件 `robot.motionStopped{reason:"operator_stop"}`
- 失败表现：只发 UDP 零帧也有效，但主机不知道是你主动停的，不会产生事件

**条目：急停**

- 实现方式：二进制报文 + JSON，双通道
- 端口：UDP 43101 连发 5 帧 + TCP 43100 一条
- 指令：UDP 头 `type=4`（EmergencyStop），连发 5 次、间隔 50 ms；同时发 operation `robot.emergencyStop`
- 报文：
  - UDP：44 字节头，`type=4`，其余字段同运动帧，载荷为空，签名同上
  - JSON：`{"operation":"robot.emergencyStop"}`
- 返回：`{"ok":true}` + 事件 `robot.emergencyStop{latched:true}`
- 失败表现：急停是锁存的，之后必须 `robot.reset` 或重新使能才能运动
- **重要**：软件急停不能替代硬线急停，现场必须保留独立急停回路

## 2.4 连接 / 使能 / 失能 / 断开（JSON）

**条目：连接底盘**

- 实现方式：JSON 请求
- 端口：TCP 43100
- 指令：`robot.connect`（`operation` 字段的值）
- 报文：

```json
{"operation":"robot.connect","data":{"settings":{"schema":13,"iniBase64":"<整份INI的base64>"}}}
```

- 前置：握手完成
- 返回：`{"ok":true,"data":{"queued":true,"settings":{...}}}`
- 后续：等事件 `robot.connectionChanged{connected:true}` 才算连上
- 失败表现：`invalid_settings`（配置非法）、`not_session_owner`（不是控制方）

> `settings` 不是键值对，是整份 INI 文件的 Base64。见第 3 章。

**条目：使能**

- 端口：TCP 43100
- 指令：`robot.enable`
- 报文：`{"operation":"robot.enable","data":{"enabled":true}}`
- 前置：底盘已连接
- 返回：`{"ok":true}` + 事件 `robot.stateChanged{stateKey:"enabled"}`
- 失败表现：`drive_not_connected`

**条目：失能**

`{"operation":"robot.enable","data":{"enabled":false}}`，车会立即停止输出。

**条目：断开底盘**

`{"operation":"robot.disconnect"}`，返回 `{"ok":true}`。

## 2.5 怎么确认车真的在动

订阅 UDP 43101 的遥测（`type=3`），解析 JSON 里的：

| 字段 | 含义 |
|---|---|
| `appliedLinearMps` | 实际执行的线速度，应接近你下发的值 |
| `appliedAngularRadps` | 实际角速度 |
| `left.wheelSpeedMps` / `right.wheelSpeedMps` | 左右轮速 |
| `commandFresh` | 指令是否新鲜（false 说明主机认为你断线了） |
| `feedbackFresh` | 电机反馈是否新鲜 |

遥测包格式见 8.2。

# 3. 底盘设置

## 3.0 先理解一个反直觉的地方

底盘参数**不是**一个个字段直接发，而是**一整份 INI 配置文件的 Base64**：

```json
{"schema":13,"iniBase64":"W2RyaXZlXQpzZXR0aW5nc1NjaGVtYVZlcnNpb249MTMKY2FuQml0cmF0ZT0..."}
```

- `schema` 必须是 `13`（配置版本号，不匹配会被拒）
- `iniBase64` 是 INI 文本的 Base64，键在 `[drive]` 组下

为什么要这样：这台车的配置项有 40 多个，还包含"每轴最多 16 台夹爪电机"的数组。逐字段发很容易半途失败，所以设计成"整包替换"。

## 3.1 改一个参数的标准流程

```
1) 先读当前配置：
   {"operation":"robot.settings.get"}
   <- {"ok":true,"data":{"settings":{"schema":13,"iniBase64":"..."}}}

2) Base64 解码，得到 INI 文本，例如：
   [drive]
   settingsSchemaVersion=13
   maximumLinearSpeedMps=0.12
   wheelRadiusM=0.07953

3) 改你要改的那一行：
   maximumLinearSpeedMps=0.08

4) 重新 Base64，发回去：
   {"operation":"robot.settings.update",
    "data":{"settings":{"schema":13,"iniBase64":"<新的base64>"}}}

5) 主机会用它重连底盘并回完整快照：
   <- {"ok":true,"data":{"protocolVersion":1,"driveConnected":true,"settings":{...}}}
```

**注意单位换算**：界面显示常用 mm/s、deg/s，INI 里是 m/s、rad/s。写错单位是第二常见故障。

| 界面显示 | INI 键 | 换算 |
|---|---|---|
| 最大线速度 120 mm/s | `maximumLinearSpeedMps` | ÷1000 → `0.120` |
| 最大角速度 50 deg/s | `maximumAngularSpeedRadps` | ×π/180 → `0.8727` |
| 轮半径 79.53 mm | `wheelRadiusM` | ÷1000 → `0.07953` |
| 轮距 147.3 mm | `trackWidthM` | ÷1000 → `0.1473` |
| 线加速度 200 mm/s² | `maximumLinearAccelerationMps2` | ÷1000 → `0.200` |
| 角加速度 57.3 deg/s² | `maximumAngularAccelerationRadps2` | ×π/180 → `1.000` |

### 为什么这里没有"电机品牌"选项

驱动轮的"品牌/协议"**绑定在通信方式上**，不是独立字段：

| `wheelCommunicationMode` | 实际走的协议 | 命令码 | 寻址 |
|---|---|---|---|
| `can` | `ServoProtocol`（伺服 CAN） | `0xA2` 速度闭环、`0x88` 运行、`0x8C` 刹车、`0x9A` 状态 | 命令 `0x140+电机ID`，反馈 `0x240+电机ID` |
| `rs485` | `MwdRs485Protocol`（MWD RS485） | `0x9C` 状态、`0x80` 停机、`0x81` 停止、`0x76` 复位 | 帧头 `0x3E` + 电机 ID |

两条链路的**命令语义、电机 ID、方向系数、限速逻辑完全相同**，只有帧封装不同，
所以配置上只需要选"接线方式"，选完协议就定了。

**夹爪不一样**：夹爪可能在同一套系统里混用不同品牌，所以它有独立的 `mode` 字段
（`ttCanopen` / `mwdRs485` / `mwdCan` / `zdtCan`），见 4.1。这也是为什么夹爪配置项比轮电机多。

**要换轮电机品牌**：不是改配置能解决的，需要在 `src/robot/wheel_motor_controller.cpp`
里新增一套协议映射（参照 `servo_protocol.cpp` / `mwd_rs485_protocol.cpp`），并升级配置 schema。
这属于二次开发，不在本接口范围内。

**条目：切换驱动轮到 CAN**

- 端口：TCP 43100
- 指令：`robot.settings.update`
- 需要改的键：`wheelCommunicationMode=can`、`wheelCanSerialPort=COM8`、`wheelCanSerialBaudRate=115200`、`wheelCanBitrate=1000000`
- 报文：按 3.1 的流程，把这四个键改好后整包 base64 发回

# 4. 夹爪与探头间距

## 4.0 结构：3 个轴，每轴最多 16 台电机

- `axis`：`0`=X 轴、`1`=Y 轴、`2`=Z 轴
- `index`：该轴内的电机序号，从 `0` 开始
- 配置存在同一份 INI 里，数组名 `clampXMotors` / `clampYMotors` / `clampZMotors`

## 4.1 电机配置项（INI 数组元素）

| 数组元素键 | 界面叫法 | 含义 | 取值 |
|---|---|---|---|
| `mode` | 通信方式 | 协议 | `ttCanopen` / `mwdRs485` / `mwdCan` / `zdtCan` |
| `serialPort` | 串口 / CAN 适配器 | 端口名 | 如 `COM5` |
| `serialBaudRate` | 串口 / 适配器波特率 | | 115200 等 |
| `canBitrate` | CAN 总线波特率 | | 500000 等 |
| `motorId` | 电机 ID | 站号 | 1..32 |
| `sign` | 方向 | 1 正向 / -1 反向 | ±1 |
| `alias` | 别名 | 主控页显示名 | 任意字符串 |
| `gearRatio` | 传动比 | 每转对应探头位移 | mm/圈，默认 10.0 |
| `upperLimit` / `lowerLimit` | 记录上限位 / 下限位 | 电机多圈角度 | 度 |
| `upperLimitEnabled` / `lowerLimitEnabled` | 限位使能 | | bool |
| `zdtFirmware` | 驱动器固件 | ZDT 专用 | `x` / `emm` |
| `zdtMaximumSpeedRpm` | 100% 对应转速 | ZDT 满速 | RPM |
| `zdtAcceleration` | 加速度 | ZDT 加速 | X 固件 RPM/s；Emm 固件 0..255 |

另有三个同轴同步开关：`clampXMotorsSync` / `clampYMotorsSync` / `clampZMotorsSync`（bool）。

### ZDT CAN 专有说明（`mode=zdtCan`）

ZDT 用厂商"自由协议"，29 位扩展帧，帧尾固定校验 `0x6B`（不是 Modbus CRC）。

**必填配置项**

| 键 | 说明 |
|---|---|
| `mode` | `zdtCan` |
| `motorId` | 1..255，同时决定 CAN 扩展帧 ID：`ID = motorId << 8` |
| `serialPort` | 小车上的 CAN 适配器串口（PCAN / Candle），不是 COM 直连电机 |
| `canBitrate` | 与驱动器一致，常见 500000 或 1000000 |
| `sign` | 方向，`1` 正向、`-1` 反向 |
| `zdtFirmware` | `x` 或 `emm`，决定速度/加速度字段宽度，填错会乱转 |
| `zdtMaximumSpeedRpm` | 100% 对应的转速（RPM） |
| `zdtAcceleration` | `x` 固件 0..65535（RPM/s）；`emm` 固件 0..255 |

**控制链路上的单位换算**

```
signedTenthsRpm = percent * sign * zdtMaximumSpeedRpm / 10
```

例：`percent=50`、`zdtMaximumSpeedRpm=100` → `500`（即 50 RPM）。
范围 ±30000（±3000 RPM），超出会被拒。

**Host 自动做的两件事**

1. **首次给速度前自动使能**：先发 `F3 AB 01 00 6B`，等驱动器应答（700 ms 超时），
   确认后才发速度帧。你在接口上只会看到 `robot.clamp.setMotorSpeed` 的 `ok:true`，
   使能是隐式的。
2. **应答超时上报**：使能或速度帧 700 ms 无应答，状态文本会提示检查
   电源 / CAN 线 / 速率 / ID / 0x6B 校验，日志类别为 `CLAMP.ZDT`。

**底层帧格式（直连 CAN 或抓包调试时用）**

| 功能 | data（十六进制） | 说明 |
|---|---|---|
| 探测在线 | `36 6B` | 连接时发，验证 ID 与校验 |
| 使能 | `F3 AB 01 00 6B` | 首次运动前必需 |
| 速度（X 固件） | `F6 [dir] [accH accL] [spdH spdL] 00 6B` | 加速度 16 位 |
| 速度（Emm 固件） | `F6 [dir] [spdH spdL] [acc] 00 6B` | 速度按整 RPM，加速度 8 位 |
| 停止 | `FE 98 00 6B` | |

- `dir`：`0` 正转、`1` 反转（符号单独占一字节，速度字段填绝对值）
- `spd`：X 固件填 `|tenthsRpm|`；Emm 固件填 `|tenthsRpm| / 10`
- 帧 ID：`(motorId << 8) | 包序号`，单帧命令包序号为 `0`

**位置能力**

`zdtCan` **支持** `robot.clamp.requestPosition` 与 `robot.clamp.moveToPosition`
（`supportsPosition()` 对 `zdtCan` 和 `mwdCan` 返回 true）。
所以基于位置的限位、探头间距定位在 ZDT 模式下可用；`ttCanopen` / `mwdRs485` 不支持。

**条目：给 X 轴加一台电机并保存**

- 端口：TCP 43100
- 指令：`robot.clamp.settings.update`
- 报文：

```json
{"operation":"robot.clamp.settings.update",
 "data":{"settings":{"schema":13,"iniBase64":"<INI 中 clampXMotors 数组多了一项>"}}}
```

- 返回：完整外设快照
- 失败表现：`invalid_settings`（夹爪配置校验失败，例如串口与通信方式不匹配）

> 数组键在 INI 文本里形如 `clampXMotors\1\mode=zdtCan`（QSettings 格式）。手写容易出错，建议按 3.1 的流程"读回来改"。

|---|---|---|

- 说明：结果可能几毫秒到几十毫秒后才到，需要按 `axis+index` 匹配

## 4.6 条目：移动到指定角度

- 端口：TCP 43100
- 指令：`robot.clamp.moveToPosition`
- 报文：

```json
{"operation":"robot.clamp.moveToPosition",
 "data":{"axis":0,"index":0,"degrees":12.5}}
```

- `degrees`：电机多圈角度，必须有限且绝对值 ≤ 1e6
- 返回：`{"ok":true,"data":{"queued":true}}`
- 到位确认：靠 `robot.clamp.position` 事件比对
- 失败表现：`invalid_argument`、`position_unsupported`

## 4.7 条目：探头间距（把"间距 mm"换算成电机角度）

界面上的「最小间距 / 目标间距 / 重置零点 / 移动到间距」是这样工作的：

| 步骤 | 谁做 | 说明 |
|---|---|---|
| 重置零点 | 你调 `requestPosition` 拿当前角度，自己记住 | **主机不存零点**，零点在上位机本地 |
| 算角度 | 你自己算 | `目标角度 = 零点角度 + (目标间距 − 最小间距) ÷ 传动比 × 360` |
| 执行 | `robot.clamp.moveToPosition` | 把算出的角度发过去 |
| 反馈 | 事件 `robot.clamp.position` | 用返回角度反算当前间距 |

- 传动比来自该电机的 `gearRatio`（mm/圈）
- 零点、最小间距、目标间距都是**上位机本地状态**，主机没有对应接口
- 所以第三方要自己持久化这三个值

**条目：移动到间距 50 mm（假设零点 0°、最小间距 10 mm、传动比 10 mm/圈）**

- 端口：TCP 43100
- 指令：`robot.clamp.moveToPosition`
- 计算：`(50 − 10) ÷ 10 × 360 = 1440°`
- 报文：`{"operation":"robot.clamp.moveToPosition","data":{"axis":0,"index":0,"degrees":1440}}`
- 返回：`{"ok":true,"data":{"queued":true}}`
- 确认：等 `robot.clamp.position{degrees:≈1440}`
- 失败表现：撞限位会收到事件 `robot.clamp.limitReached{axis,index,upper:true}`

**写入（TCP 43100）**

```json
{"operation":"ultrasound.parameters.apply","data":{"changes":[
  {"method":"setGain","args":[35.5,-1],
   "readbackMethod":"getGain","readbackArgs":[-1]},
  {"method":"setWedgeAngle","args":[18.5,-1],
   "readbackMethod":"getWedgeAngle","readbackArgs":[-1]}
]}}
```

- `changes` 一次可放 1..512 条（超了返回 `invalid_parameter_batch`）
- `method` 必须以 `set` 开头，`readbackMethod` 必须以 `get` 开头，否则该条被拒
- 主机逐条"写入 → 立刻回读"，成功项的**回读值**放在 `readbacks` 里
- 返回：

```json
{"ok":true,"data":{
  "readbacks":{"getGain:Wy0xXQ==":35.5,"getWedgeAngle:Wy0xXQ==":18.5},
  "errors":[],"limitMessage":""}}
```

- 任一条失败 → `ok=false`、`errorCode="parameter_apply_partial"`，失败详情在 `errors`

> `readbacks` 的键是 `方法名:base64(args 的 JSON)`。`[-1]` 的 base64 是 `Wy0xXQ==`。你不用解析这个键，用 `errors` 判断失败、用 `getMany` 主动读确认。

**读取（TCP 43100）**

```json
{"operation":"ultrasound.parameters.getMany","data":{"requests":[
  {"method":"getGain","args":[-1]},
  {"method":"getFrameRate","args":[]}
]}}
```

返回 `{"values":{"getGain:Wy0xXQ==":35.5,...},"errors":[]}`

**参数约定**

| 规则 | 说明 |
|---|---|
| `args` 顺序 | 与 SDK 签名一致；绝大多数是 `[值, groupId]`（set）或 `[groupId]`（get） |
| `groupId` | 超声工作组号，`-1` 表示当前组；多组探头时填具体组号 |
| 单位 | 角度=度，深度=mm，声速=m/s，频率=MHz，脉宽=ns |
| 参数个数不符 | 错误文本为 `参数个数错误：期望 N，收到 M` |

# 6. 超声功能

## 6.1 条目：连接超声设备

- 实现方式：JSON 请求
- 端口：TCP 43100
- 指令：`ultrasound.device.connect`
- 报文：

```json
{"operation":"ultrasound.device.connect","data":{"address":"127.0.0.1","deviceId":0}}
```

- `address`：超声 SDK 服务地址，同机运行填 `127.0.0.1`
- `deviceId`：设备编号，单机填 `0`
- 返回：`statusSnapshot`，关键字段 `hardwareOnline:true`、`serviceConnected:true`
- 失败表现：`device_connect_failed`；`ok=false` 时看 `errorText`
- 前置：主机上的超声 SDK 服务必须先启动（这不是本接口能启动的）

## 6.2 条目：开始采集

- 端口：TCP 43100
- 指令：`ultrasound.acquisition.start`
- 报文：`{"operation":"ultrasound.acquisition.start"}`
- 前置：`ultrasound.device.connect` 成功，且 `hardwareOnline=true`
- 返回：`statusSnapshot`，`capturing:true`
- 失败表现：`acquisition_start_failed`
- 之后：超声帧开始从 UDP 43102 发出（见 8.3）

## 6.3 条目：停止采集 / 断开设备

| 功能 | 指令 | 报文 |
|---|---|---|
| 停止采集 | `ultrasound.acquisition.stop` | `{"operation":"ultrasound.acquisition.stop"}` |
| 断开设备 | `ultrasound.device.disconnect` | `{"operation":"ultrasound.device.disconnect"}` |
| 查询状态 | `ultrasound.status` | `{"operation":"ultrasound.status"}` |

返回都是 `statusSnapshot`。

`statusSnapshot` 就是响应的 `data`，结构是：

```json
{"device":{"available":true,"serviceConnected":true,"hardwareOnline":true,
           "capturing":true,"captureReady":true,"startPending":false,
           "pointCount":1024,"maxAmplitudeValue":2048,"currentGroup":0,
           "totalFrames":12345,"displayDropped":0,"scanDropped":0,
           "scanQueueBytes":0,"scanQueueDepth":0},
 "ownerSessionId":"7","decoderAvailable":true,"timeMs":123456.7}
```

**设备字段都在 `data.device` 下面，不要直接在 `data` 上取。**

| `device` 字段 | 含义 |
|---|---|
| `available` | 服务对象是否存在 |
| `serviceConnected` | 与 SDK 服务的连接 |
| `hardwareOnline` | 硬件是否在线 |
| `capturing` | 是否在采集 |
| `captureReady` | 是否可出图 |
| `startPending` | 启动中 |
| `pointCount` | 每束采样点数 |
| `maxAmplitudeValue` | 当前最大幅值档位（2048/4096/8192/16384） |
| `currentGroup` | 当前组号 |
| `totalFrames` | 累计帧数 |
| `displayDropped` / `scanDropped` | 显示/扫查丢包数 |
| `scanQueueBytes` / `scanQueueDepth` | 扫查队列积压 |

顶层还有 `ownerSessionId`（谁在控制）、`decoderAvailable`（解码器是否就绪）、`timeMs`。

## 6.4 条目：读全部参数快照

- 端口：TCP 43100
- 指令：`ultrasound.parameters.snapshot`
- 报文：`{"operation":"ultrasound.parameters.snapshot"}`
- 返回：

```json
{"ok":true,"data":{
  "values":{"getGain:Wy0xXQ==":35.5, "getFrameRate:W10=":1000, "...":0},
  "complete":true,
  "configBase64":"<当前配置备份>",
  "errors":[],
  "status":{...}}}
```

- `complete:false` 说明部分参数读取失败，看 `errors`
- 首次接入建议先调这个，把所有参数拉一遍做基线

## 6.5 条目：提交参数到预设并保存

- 端口：TCP 43100
- 指令：`ultrasound.parameters.commit`
- 报文：`{"operation":"ultrasound.parameters.commit","data":{"presetId":2}}`
- 作用：把当前硬件参数**捕获进指定预设**并落盘，同时做 PRF 限幅
- 返回：`presetState`（含 `presets`、`currentPreset`）
- 失败表现：`invalid_preset`、`preset_capture_failed`、`pulse_limit_failed`
- 说明：`apply` 只改硬件不落盘；要持久化必须再调 commit

## 6.6 条目：扫查精度与编码器标定

| 功能 | 指令 | 报文 | 返回 |
|---|---|---|---|
| 读扫查精度 | `ultrasound.scan.precision.get` | `{"presetId":2}` | `{"presetId":2,"mmPerCell":0.25}` |
| 写扫查精度 | `ultrasound.scan.precision.set` | `{"presetId":2,"mmPerCell":0.25}` | 空 data |
| 读编码器标定 | `ultrasound.encoder.calibration.get` | 无 data | `{"wheelDiameterMm":500,"resolution":4096}` |
| 写编码器标定 | `ultrasound.encoder.calibration.set` | `{"wheelDiameterMm":500,"resolution":4096}` | 空 data |
| 编码器清零 | `ultrasound.encoder.reset` | 无 data | 空 data |

- `mmPerCell` 是扫查图谱上"一格多少毫米"，界面叫「B/C 路径精度」
- `wheelDiameterMm` 必须 > 0 且有限，`resolution` 必须 > 0
- 失败表现：`invalid_encoder_calibration`、`encoder_calibration_failed`、`scan_precision_failed`

# 8. 数据回传

## 8.0 媒体通道通用规则（超声/激光/相机/IMU 都适用）

### 为什么要分片

一张超声帧或点云可能几百 KB，UDP 单包最多 1472 字节，所以要拆。每片自带序号，收齐再拼。

### 58 字节头

| 偏移 | 长度 | 字段 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 4 | magic | u32 | `0x50413136`，字节 `36 41 31 50` |
| 4 | 2 | version | u16 | `1` |
| 6 | 1 | flags | u8 | 固定 `1`（表示带签名） |
| 7 | 1 | kind | u8 | 流类型，见下表 |
| 8 | 8 | sessionId | u64 | 会话号 |
| 16 | 2 | streamId | u16 | 数据流标识 |
| 18 | 8 | messageId | u64 | 消息号，同流内递增 |
| 26 | 8 | sequence | u64 | 全通道递增 |
| 34 | 8 | timestampUs | u64 | 采集时间 |
| 42 | 4 | totalBytes | u32 | 整条消息字节数 |
| 46 | 4 | fragmentIndex | u32 | 本片序号，从 0 开始 |
| 50 | 4 | fragmentCount | u32 | 总片数 |
| 54 | 4 | payloadLen | u32 | 本片载荷长度，≤1398 |
| 58 | 16 | 签名 | bytes | HMAC-SHA256(前 58+N 字节, key)[0..15] |

单报总长 ≤ 1472 字节，所以每片载荷 ≤ 1398 字节。

### 必须先发心跳

进 43102 后**先每 500 ms 发一个心跳包**，否则主机不知道往哪发，会丢弃所有媒体（日志里是 `droppedNoPeer`）。

心跳包：同一个 58 字节头，`kind=1`、`streamId=0`、`payloadLen=0`、签名照算。

### 组装步骤

```
1. 收到包，先按 magic/version/flags 校验
2. 用 sessionId 找密钥，校验 16 字节签名（对 前58+N 字节 算 HMAC-SHA256 取前16）
3. 按 streamId 分桶；若 messageId 比桶里的新，清空桶重来（旧帧丢弃）
4. 把 payload 按 fragmentIndex 放进数组，累计到 fragmentCount
5. 拼接后总长度必须等于 totalBytes，否则丢弃
6. 得到完整消息，再按 8.3~8.6 的格式解析
```

**超时规则**：同一 `messageId` 的分片 1500 ms 内没收齐就整条丢弃，不要一直等。新 `messageId` 到达时也同样丢弃旧的。

### kind 与 streamId 对照

| kind | 名称 | streamId | 内容 |
|---|---|---|---|
| 1 | Heartbeat | 0 | 心跳，无载荷 |
| 2 | UltrasoundFrame | `0x0100 + 组号` | 超声帧 |
| 5 | LaserPointCloud | `0x0202` | 激光预览点云 |
| 6 | UsbCameraImage | `0x0300 + slot` | 相机 JPEG |
| 9 | ImuSample | `0x0203` | IMU 姿态 |
| 10 | LaserProfileObservation | `0x0204` | 焊道完整观测 |

`0x0201`（激光灰度图）和 `0x0401`（纠偏状态）在当前版本**不再发送**，不要等它们。

### 先解压，再看 7 字节头

**顺序很重要**：`PAD1` 头本身也在压缩包里面。正确顺序是"先 qUncompress 整条载荷，再读前 7 字节"，不是"跳过 7 字节再解压"。

解压后的明文开头：

| 偏移 | 长度 | 字段 | 值 |
|---|---|---|---|
| 0 | 4 | magic | `0x50414431`，字节 `31 44 41 50`（"PAD1" 的小端） |
| 4 | 2 | version | `1` |
| 6 | 1 | type | 1..6，决定后面怎么解析 |

type 3（JPEG）例外：它没有压缩，所以直接读前 7 字节即可。

type 1/2/4/5/6 整体是 **qCompress 压缩**的。解压方法：

```
qCompress 格式 = [4字节 大端 原始长度] + [zlib 数据流]
用 Qt：qUncompress(payload)
非 Qt：先读前 4 字节大端得到长度，再用 zlib 解压剩余部分
```

type 3（JPEG）是**唯一不压缩**的类型，因为 JPEG 自身已压缩。

## 8.3 超声帧（UDP 43102，kind=2，streamId=`0x0100+组号`）

完整载荷 = `qCompress(PAD1头 + type=1 + 帧体)`，所以要先 `qUncompress`，再跳过 7 字节头。

解压后的帧体按顺序：

```
u32 beamCount
  重复 beamCount 次：
    u32 pointCount
    pointCount × i16 采样值
u32 measurementCount
  重复 measurementCount 次（每条固定 32 字节）：
    u32 amplitudeA, amplitudeB, amplitudeC, amplitudeI
    u32 positionA,  positionB,  positionC,  positionI
u32 eScanImageBytes
  eScanImageBytes 字节 PNG（E 扫截图，可能为 0）
u8  frameError            // bool，1 字节
i32 scannerIo
i32 multiFrame
i32 frameNumber
u8  encoderTriggerError   // bool，1 字节
u8  encoderSyncError      // bool，1 字节
5 × i32 encoder           // 注意是 5 个，不是 4 个
u64 timestamp
i32 sourceBeamCount
i32 selectedSourceBeam    // 默认 -1
```

解析伪代码（C++/Qt）：

```cpp
QByteArray plain = qUncompress(payload);        // 先解压整条
QByteArray raw   = plain.mid(7);                // 再跳过 PAD1(4)+ver(2)+type(1)
QDataStream in(raw);
in.setByteOrder(QDataStream::LittleEndian);
in.setVersion(QDataStream::Qt_6_0);
quint32 beamCount; in >> beamCount;
for (quint32 b = 0; b < beamCount; ++b) {
    quint32 points; in >> points;
    QVector<qint16> samples(points);
    for (quint32 i = 0; i < points; ++i) in >> samples[i];
}
// 之后按上面的顺序继续读
```

- `0x0100 + 组号`：组 0 就是 `0x0100`
- 同一组的新帧到达时，旧帧直接丢弃（不需要排队）

## 8.4 激光预览点云（UDP 43102，kind=5，streamId=`0x0202`）

解压后可能是 type 4 或 type 5：

**type 4（float）**

```
u32 pointCount
pointCount × (f32 x, f32 y, f32 z)
```

**type 5（量化，体积减半）**

```
u32 pointCount
f32 originX, originY, originZ
f32 scale
pointCount × (i16 qx, i16 qy, i16 qz)
```

还原公式：`x = originX + qx * scale`，y/z 同理。

- 坐标单位是米，坐标系为激光相机坐标系
- NaN/无效点会以 type 4 原样下发，解析时需跳过非有限值

## 8.5 焊道完整观测（UDP 43102，kind=10，streamId=`0x0204`）

这个流同样用 **qCompress 压缩**，解压后结构为：

```
PAD1(4) + ver(2) + type=6(1)
u32 pointCount
pointCount × (f32 x, f32 y, f32 z)
u32 frameNumber
i64 receivedAtEpochMs
u32 fieldCount            // 固定 52
以下按顺序 52 个字段：
  bool 类写 u8，枚举与整数写 i32，浮点写 f64，字符串写 QString
  valid, profileDetectionMode, profileDetectionReason, horizontal,
  baselineSupported, baselineOffsetPx, ... 其余按结构声明顺序
```

- `fieldCount` 允许未来增减：读到多少算多少，多出的忽略，少的用默认值
- 前 6 个字段足够判断"本帧有没有焊道"：`valid`、`profileDetectionMode`、`profileDetectionReason`、`horizontal`、`baselineSupported`、`baselineOffsetPx`

## 8.6 相机画面（UDP 43102，kind=6，streamId=`0x0300+slot`）

```
PAD1(4) + ver(2) + type=3(1)
u32 jpegBytes
jpegBytes 字节 JPEG 数据
```

直接交给 JPEG 解码器即可，没有宽高字段（JPEG 自带）。

## 8.8 整包扫查批次（TCP 43103）

用于"不能丢"的完整扫查数据。

**28 字节头**

| 偏移 | 长度 | 字段 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 4 | magic | u32 | `0x50413136` |
| 4 | 2 | version | u16 | 1 |
| 6 | 2 | kind | u16 | `2` = UltrasoundScanBatch |
| 8 | 8 | sessionId | u64 | 会话号 |
| 16 | 8 | sequence | u64 | 递增，回退会断链 |
| 24 | 4 | payloadLen | u32 | ≤32 MiB |
| 28 | 16 | 签名 | bytes | HMAC-SHA256(前 28+N 字节, key)[0..15] |

**连接流程**

```
1. TCP connect 192.168.1.20:43103
2. 直接发一帧 kind=1 心跳（或等主机先发）
3. 主机用帧头里的 sessionId 找密钥校验 HMAC
4. 校验通过后才能收到 kind=2 数据
```

**payload 结构** = `qCompress(PAD1头 + type=2 + 明文)`：

```
u32 frameCount
重复 frameCount 次：
  i32 groupId, i32 triggeredModes, i32 bColumn, i32 cColumn, i32 cRow
  i32 cGateMask, i32 amplitudeScale, f64 rangeStart, f64 rangeEnd
  然后是一帧完整的超声帧体（结构同 8.3 的帧体）
```

> `bColumn` 可能是 `-1`（尚未触发），所以按有符号 i32 读，不要按 u32。

# 9. 错误码

所有业务失败都在响应里：`{"ok":false,"errorCode":"...","errorText":"..."}`。

| errorCode | 出现场景 | 你该做什么 |
|---|---|---|
| `not_session_owner` | 你的会话不是控制方 | 重新握手，或先让原控制方退出 |
| `unsupported_operation` | operation 写错 | 对照本手册拼写 |
| `invalid_operation` / `invalid_request` | 缺 operation / payload 不是 JSON 对象 | 检查帧头 payloadLen 与 JSON 编码 |
| `invalid_argument` | 字段缺失、越界、类型不对 | 看 errorText |
| `invalid_settings` | 配置包不合法 | 检查 schema=13、键名、单位 |
| `handshake_required` | 没握手就发请求 | 先发 Hello |
| `unsupported_message` | 发了不允许的帧类型 | 握手后只能 Request/Ping |
| `drive_not_connected` | 底盘没连 | 先 `robot.connect` |
| `drive_not_enabled` | 没使能 | 先 `robot.enable` |
| `sensor_service_unavailable` | IMU/激光服务未就绪 | 检查主机上对应服务 |
| `camera_service_unavailable` | 相机服务未就绪 | 同上 |
| `clamp_service_unavailable` | 夹爪服务未就绪 | 同上 |
| `position_unsupported` | 该电机不支持读位置 | 换支持位置反馈的协议 |
| `correction_service_unavailable` | 纠偏线程未启动 | 重启主机 |
| `correction_busy` | 纠偏已在跑 | 先 stop |
| `correction_not_active` | 没在跑却调 pause | 先 start |
| `laser_not_connected` | 纠偏要求激光在线 | 先 `robot.laser.connect` |
| `invalid_host_limits` | 车体几何未标定 | 先设置轮径/轮距 |
| `invalid_parameter_batch` | 参数批次为空或超 512 | 拆分批次 |
| `invalid_parameter_set` | 单条 set 结构非法 | 检查 method/args/readback 三件套 |
| `parameter_write_failed` | SDK 拒绝写入 | 看 errorText |
| `parameter_readback_failed` | 写成功但回读失败 | 重试或降级 |
| `parameter_apply_partial` | 批量中部分失败 | 看 `errors` 数组逐条处理 |
| `pulse_limit_failed` | PRF 限幅失败 | 降低帧率后重试 |
| `invalid_preset` / `preset_in_use` / `preset_capture_failed` | 预设相关 | 换 ID 或先切换当前预设 |
| `invalid_import` | 预设导入内容非法 | 检查 Base64 与 JSON |
| `invalid_decoder_settings` | 解码组配置非法 | 按 6.8 的约束逐项检查 |
| `device_connect_failed` | 超声设备连不上 | 确认主机上 SDK 服务在跑 |
| `acquisition_start_failed` | 启动采集失败 | 确认 `hardwareOnline=true` |
| `invalid_encoder_calibration` / `encoder_calibration_failed` | 编码器标定 | 直径 >0、分辨率 >0 |
| `scan_precision_failed` | 扫查精度保存失败 | 检查 presetId |
| `sdk_exception` | 厂商 SDK 抛异常 | 主机已捕获，通常伴随硬件掉线 |

## 9.1 "没有报错但没反应"的排查

| 现象 | 最可能的原因 |
|---|---|
| 发 UDP 车不动 | 没 `robot.connect` / 没 `robot.enable` / 签名算错 |
| 发 UDP 车动一下就停 | 没按 50 ms 连续发；`ttlMs` 填太小 |
| TCP 请求一直超时 | 没发 Ping 被断开；`sequence` 重复或回退；`sessionId` 用错 |
| 收不到任何媒体 | 没先发媒体心跳；`sessionId` 不匹配；HMAC 算错 |
| 收到媒体但解不出 | 忘了跳过 7 字节 PAD1 头；没解 qCompress；`qCompress` 前 4 字节没剥离 |
| 超声帧点数与预期不符 | 没下发 `ultrasound.decoder.settings`，或 `pointCount` 不一致 |
| 参数写成功但值没变 | 只调了 `apply` 没调 `commit`，预设切换后被覆盖 |

# 10. 端到端联调示例

## 10.1 只调超声参数（最小闭环）

```
1. TCP connect 192.168.1.20:43100
2. → Hello{protocolVersion:1, clientId:"App"}
3. ← HelloAck{sessionId:"1", sessionToken:"..."}
4. → Request{operation:"ultrasound.device.connect",
             data:{address:"127.0.0.1", deviceId:0}}
5. ← Response{ok:true, data:{available:true, hardwareOnline:true,...}}
6. → Request{operation:"ultrasound.parameters.apply",
             data:{changes:[{method:"setGain",args:[35.5,-1],
                             readbackMethod:"getGain",readbackArgs:[-1]}]}}
7. ← Response{ok:true, data:{readbacks:{...:35.5}, errors:[], limitMessage:""}}
8. → Request{operation:"ultrasound.parameters.commit", data:{presetId:2}}
9. ← Response{ok:true, data:{presets:[...], currentPreset:2, ...}}
```

第 8 步不能省，否则重启或切预设后参数丢失。

## 10.2 让小车前进 0.08 m/s 再停

```
1. TCP 握手 → sessionId / sessionToken
2. → robot.connect {settings:{schema:13, iniBase64:"..."}}
3. ← ok，等事件 robot.connectionChanged{connected:true}
4. → robot.enable {enabled:true}
5. ← ok，等事件 robot.stateChanged{stateKey:"enabled"}
6. 解出 key = base64_decode(sessionToken)
7. 每 50 ms 发一帧 MotionSetpoint（linearMilliMps=80, angularMilliRadps=0, ttlMs=200）
8. 收 UDP 遥测，确认 appliedLinearMps ≈ 0.08
9. 停车：发一帧 0/0，再发 robot.motion.stop
```

关键 C++ 片段（Qt）：

```cpp
QByteArray sign16(const QByteArray& body, const QByteArray& key) {
    QMessageAuthenticationCode mac(QCryptographicHash::Sha256, key);
    mac.addData(body);
    return mac.result().left(16);
}

QByteArray buildMotionDatagram(quint64 sessionId, quint64 sequence,
                               quint64 timestampUs, qint32 linearMilliMps,
                               qint32 angularMilliRadps, const QByteArray& key) {
    QByteArray body;
    QDataStream out(&body, QIODevice::WriteOnly);
    out.setByteOrder(QDataStream::LittleEndian);
    out.setVersion(QDataStream::Qt_6_0);
    out << quint32(0x50413136)      // magic
        << quint16(1)               // version
        << quint8(2)                // type = MotionSetpoint
        << quint8(1)                // flags = 带签名
        << quint64(sessionId)
        << quint64(sequence)
        << quint64(timestampUs)
        << quint16(200)             // ttlMs
        << qint32(linearMilliMps)
        << qint32(angularMilliRadps)
        << quint16(0);              // payloadLen
    return body + sign16(body, key);
}
```

## 10.3 收一帧超声图像

```
1. 握手，拿 sessionId + key
2. 向 192.168.1.20:43102 每 500 ms 发心跳（kind=1, streamId=0）
3. 收 UDP 包 → 校验 magic/version/flags → 校验 HMAC
4. 按 streamId 分桶（0x0100 起）
5. 收齐 fragmentCount 片 → 拼接 → 校验 totalBytes
6. 校验 PAD1 头 → type 应为 1 → qUncompress → 按 8.3 解析
```

组装核心：

```cpp
struct Assembly {
    quint64 messageId = 0;
    quint32 totalBytes = 0, fragmentCount = 0;
    QHash<quint32, QByteArray> parts;
};
QHash<quint16, Assembly> buckets;

void onDatagram(const QByteArray& dg) {
    // 1) 解析 58 字节头（略），得到 streamId/messageId/fragmentIndex/fragmentCount/totalBytes/payload
    // 2) 校验 HMAC：HMAC-SHA256(dg.left(58 + payloadLen), key).left(16) == dg.right(16)
    Assembly& a = buckets[streamId];
    if (messageId > a.messageId) { a = Assembly{}; a.messageId = messageId; }
    a.parts.insert(fragmentIndex, payload);
    if (a.parts.size() == int(fragmentCount)) {
        QByteArray full;
        for (quint32 i = 0; i < fragmentCount; ++i) full += a.parts.value(i);
        if (quint32(full.size()) == totalBytes) {
            // full 整体是 qCompress 包
            QByteArray plain = qUncompress(full);
            QByteArray frame = plain.mid(7);   // 再跳过 PAD1 + ver + type
            // 按 8.3 的字段顺序解析
        }
        buckets.remove(streamId);
    }
}
```

# 11. 只能在本机做、没有接口的功能

这些是上位机软件自己的功能，**主机上没有对应接口**。第三方要自己实现等价逻辑。

| 功能 | 界面位置 | 为什么没有接口 | 你要做的话 |
|---|---|---|---|
| 录制原始帧 / 回放 | 数据面板、文件菜单 | 主机只负责把帧发出来，存不存由客户端决定 | 自己把 8.3 的帧写文件 |
| 扫描会话存档 / 载入 | 数据面板 | 同上，是本地文件格式 | 自己设计存储格式 |
| 屏幕布局 / 双屏 | 工具菜单 | 纯 UI | 自己处理 |
| 远程桌面 | 工具菜单 | 启动外部 `LanRemoteQt.exe` | 自己用系统远程桌面 |
| 加载/保存设备配置（本地） | 文件菜单 | 本地 QSettings 快捷方式 | 用 `robot.settings.get/update` 代替 |
| 接口日志文本框 | 小车配置页 | 本地显示 | 自己记录 `robot.peripheral.log` 事件 |
| 焊道模板管理 | 小车控制页 | 模板是本地数组，随 `autoCorrection.start` 的 settings 下发 | 自己构造 `profileTemplates` |
| 表面跟踪（搜索窗口/阈值/跟随闸门） | 参数面板·闸门 | 纯上位机算法，不入协议 | 自己实现：跟踪表面位置后动态改 Gate 的 Start/End |
| B/C 扫显示参数（色带/Gamma/刻度/低切） | 主界面 | 纯渲染 | 自己决定配色 |
| E/B/C 扫"启动"开关 | 主界面 | 纯视图缓存开关 | 自己决定是否渲染 |
| 交汇深度比例 / PCS | 参数面板·探头 | 本机公式 `PCS = 2 × d × tanθ` | 自己算 |
| 探头间距零点 / 最小/目标间距 | 探头调节页 | 本机记的三个值 | 自己持久化（见 4.7） |
| 手动输出滑块（5–100%） | 小车控制页 | 只是把速度乘一个系数 | 自己乘 |
