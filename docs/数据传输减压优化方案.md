# 数据传输减压优化方案与实测报告

> 版本：2026-11-09  
> 目标：在不影响任何功能与算法的前提下，降低小车端 → 操作端的数据压力  
> 用户确认的约束：操作端只负责显示与下发指令；计算与执行全部在小车端；所有面板必须持续推送（不做「不可见就停流」）；允许两端同步升级协议；主 KPI 为网络带宽

---

## 1. 链路拓扑与基线诊断

```
激光轮廓仪 MV3DLP ──USB(本地, 17.6 MB/s)──┐
USB/网络相机 ────────────────────────────┤
超声设备 ────────────────────────────────┤
                                          ▼
                          小车端 PA1664RobotHost (192.168.1.20)
                                          │
        ┌─────────────────┬───────────────┼────────────────┐
   43100 TCP           43101 UDP       43102 UDP       43103 TCP
   控制/事件/日志      遥测20Hz/运动     6 路媒体流     超声扫描批次
                                          │
                          操作端 PA1664Workbench (192.168.1.100)
```

### 诊断出的浪费点

| 类别 | 发现 | 证据 |
|---|---|---|
| 无人消费的流 | 激光灰度图 `0x0201` 在操作端只赋值给 `m_laserImage`，全仓无读取点 | `robotcontrolpanel.cpp` `setLaserProfileImage()` |
| 重复通道 | 同一条外设日志走 `robot.log` + `robot.peripheral.log` 两条 TCP 事件，控制台重复显示 | `robot_peripheral_host_service.cpp:1646`、`host_application.cpp:175` |
| 重复通道 | 纠偏状态 JSON 同时走媒体 `0x0401` 与控制事件 | `robot_peripheral_host_service.cpp:1619` |
| 双提交路径 | 同一帧图像经 `cameraImageFrameChanged`(50ms) 与 `correctionCameraFrameReady`(逐帧) 两次进编码邮箱 | `robot_peripheral_host_service.cpp:459`、`471` |
| 编码开销 | 点云每点 float32×3=12 B；原始单行轮廓可达 2048 点 | `workbench_data_codec.cpp:310` |
| 分片开销 | 媒体分片有效载荷 1126 B，头 58 B + HMAC 16 B = 6.6% 开销 | `media_channel.cpp:16`、`media_codec.cpp:50` |
| 速率错配 | USB 相机 15 Hz 推送，操作端 UI 100 ms 才刷新一次 | `kUsbImageIntervalMs=66` vs `refreshVisibleUi()` |
| 冗余包 | 驾驶时 250 ms 心跳与 50 ms 运动包重复（服务端已把运动包当心跳） | `realtime_channel.cpp:67`、`429` |
| 接收侧 | JPEG 解码、`qUncompress` 在 UI 线程逐包执行 | `robotcontrolpanel.cpp:1178` |

### 关键前提修正（实测发现）

- **激光采集 17.6 MB/s ≈ 141 Mbps 走的是小车端本地 USB**（`connectBySerial`），**不经过以太网**；`SCAN_INGEST_TELEMETRY` 中 `displayDrop` 占 99.8%、`drop=0`，属于显示端主动丢旧帧，不是网络丢包
- **profile 模式下 `0x0201` 本来就不发**（depth 帧不产生灰度预览图），该流只在图像模式存在
- 实测 USB 相机约 **0.5 fps**（每 2 秒 1 帧 ~35 KB），并非 15 fps 实时视频
- 两端网口均为 **100 Mbps**（开发机 `Realtek USB FE` 为硬上限；小车端 `Intel I226-V` 是 2.5G 网卡但协商到 100 Mbps）

## 2. 已实施的改动

| 阶段 | 内容 | 主要文件 |
|---|---|---|
| P0 | 逐流字节埋点：`MEDIA.TX` 增加 `streams=0x....:消息数/字节数`，新增 `BULK.TX` 窗口统计，超声实时帧纳入统计；操作端 5 s 接收日志增加逐流字节、UDP 数据报/完成数/组装超时 | `host_application.*`、`remote_workbench_session.*`、`robotcontrolpanel.*` |
| P1 | 停止发布 `0x0201`（无人消费），合并图像双提交路径，外设日志改单通道，纠偏状态改单通道（保留可靠 TCP 事件） | `robot_peripheral_host_service.*` |
| P2 | 媒体分片有效载荷 1126 → **1398 B**（`kMediaDatagramBytes=1472`，填满以太网 MTU）；实时通道保持 1200 B；两端同步升级 | `protocol_types.h`、`media_codec.cpp`、`media_channel.cpp` |
| P3 | 点云量化编码 type 5（每点 12 B → 6 B，逐帧 origin/scale，含非有限点时自动回退 float 编码保持语义）；USB 相机 15 Hz → 10 Hz（与 UI 刷新对齐） | `workbench_data_codec.*`、`robot_peripheral_host_service.cpp` |
| P5 | 操作端重解码改为 30 ms 节拍的「最新值邮箱」合流缓冲（突发不再堵塞 UI 线程，稳态 1:1 不变）；驾驶期间跳过冗余心跳 | `robotcontrolpanel.*`、`realtime_channel.cpp` |

### 主动放弃的改动（附理由）

| 项 | 理由 |
|---|---|
| 遥测二进制化 | JSON 遥测仅约 12 KB/s（占 100M 链路 0.01%），收益趋零却要改底盘遥测全链路，风险大于收益 |
| 静止时空运动包降频 | 服务端租约过期会触发 `safetyStop` 事件与状态文本变化，属于功能可见语义；且会降低 UDP 丢包容忍度 |
| 超声批量深改（P4） | 实测 `BULK.TX` 无数据（E 扫只走实时帧），且批量是 C 扫完整性数据；在带宽仅 0.2 Mbps 时改动它不划算 |
| 日志降噪 | 日志写本地磁盘，不经网络；去重已在 P1 完成 |

## 3. 实测 A/B 结果

### 采集条件

- 小车端 `192.168.1.20`，先部署 P0 纯埋点版采集基线，再部署完整优化版
- 操作端 `bin\PA1664Workbench.exe`（15:28 构建，含新分片尺寸），联机约 20 分钟
- 现场流：`0x0202` 激光点云（20 Hz）、`0x0203` IMU（20 Hz）、`0x0100` 超声实时帧（20 Hz）、`0x0300/0x0301` USB 相机（约 0.5 fps）

### 严格对比（相同流组合、均含超声实时帧，每 2 秒窗口）

| 指标 | 优化前 | 优化后 | 变化 |
|---|---:|---:|---:|
| 总媒体字节（均值） | 55,280 B | 52,230 B | **-5.5%** |
| `0x0202` 点云均值 | 8,382 B | 8,574 B | 持平 |
| `0x0202` 点云峰值 | 19,866 B | 14,137 B | **-29%** |
| `0x0100` 超声实时帧 | 44,029 B | 44,026 B | 未改 |
| `0x0203` IMU | 2,868 B | 2,860 B | 未改 |

### 大范围对比（含偶发「原始 2048 点单行轮廓」大帧）

| 指标 | 优化前（470 窗口） | 优化后（59 窗口） | 变化 |
|---|---:|---:|---:|
| `0x0202` 每窗口均值 | 16,775 B | 9,314 B | **-44%** |
| `0x0202` 每窗口峰值 | 190,938 B | 50,665 B | **-73%** |

### 操作端接收侧（5 秒窗口，`[PANEL] 媒体接收` 日志）

```
包=295 字节=136058 激光图=0 点云=100 相机1=0 相机2=0 IMU=100
组装超时=2 数据报=53558 完成=50528
流=0x0100:108734, 0x0202:20124, 0x0203:7200
```

- 无点云/图像解码错误，`激光图=0`（流已移除）
- `组装超时` 累计稳定不增长；数据报与完成数接近 1:1（新分片尺寸让绝大多数消息单包送达）
- 总接收约 27 KB/s ≈ **0.2 Mbps**

## 4. 结论与建议

1. **网络不是当前瓶颈**。实测总媒体带宽约 26 KB/s（0.2 Mbps），仅占 100M 链路的 0.2%；`1000M` 网口或换网线对当前卡顿没有帮助。
2. 本轮优化的真实价值在于**削峰与去重**：偶发大帧峰值 -73%（190 KB → 51 KB）、日志/状态双通道去重、分片数 -20%、UI 线程解码不再被突发拖住；平均带宽降幅小（-5.5%）是因为 80% 流量来自未改动的超声实时帧。
3. **真正的数据压力在小车端本地**：激光 USB 采集 17.6 MB/s、8750 fps、`displayDrop` 99.8%。若现象是画面卡顿/丢帧，应优化小车端采集到显示的链路（本地降采样、渲染节流、日志写入），而不是网络。
4. 若后续启用 **C 扫批量采集**（`BULK.TX`），才会产生真正的网络重负载；届时再评估 P4 与千兆链路，判据是 `BULK.TX bytes/2s` 是否逼近 100M 有效吞吐（约 11 MB/s）。
5. 相机当前约 0.5 fps，若本应为实时视频，需先排查相机采集/网络流本身，这不属传输层问题。

## 5. 联机期间修复的环境问题（非本次优化引入）

**现象**：点击「启动 E 扫」报 `ultrasound.acquisition.start 失败 [unsupported_operation]：主机不支持操作`。

**根因**：小车端 `app\configs\` 缺少 `ultrasound_device_0` 目录，且 `generic_0\prefs.json` 为 0 字节；超声服务初始化读偏好文件时抛 `json parse error: empty input`，`GuardedThread` 异常处理把 `ultrasound_` 置空（`host_application.cpp:430`），导致所有 `ultrasound.*` 请求落到兜底分支。该异常在本次改动之前的 14:13 日志里已存在。

**修复**：
```
scp -r bin\configs\ultrasound_device_0 a@192.168.1.20:C:/Users/a/Desktop/robot_host/app/configs/
写入 {"prefs": []} 到 app\configs\generic_0\prefs.json
重启 PA1664RobotHost.exe
```
修复后日志：`ULTRASOUND 1 [设备] 已收到真实设备数据：USB 硬件在线`，`0x0100` 实时帧流正常，不再有 `unsupported_operation`。

## 7. 回滚步骤

```powershell
# 1. 小车端回退到原始主程序（部署前备份）
ssh a@192.168.1.20 "chcp 65001 >nul && taskkill /F /IM PA1664RobotHost.exe"
# PA1664RobotHost.exe.bak_p0            = 优化前原始版
# PA1664RobotHost.exe.bak_p0instrumented = P0 纯埋点版
ssh a@192.168.1.20 "copy /Y C:\Users\a\Desktop\robot_host\app\PA1664RobotHost.exe.bak_p0 C:\Users\a\Desktop\robot_host\app\PA1664RobotHost.exe"
# 2. 重新启动（用独立会话，避免 SSH 断开后进程被回收）
powershell -NoProfile -ExecutionPolicy Bypass -File .codebuddy\start_remote_host.ps1
```

代码层回滚按阶段独立：P2/P3 的线格式变更（`1398 B` 分片、type 5 点云）**必须两端同时回退**，否则混合版本会丢媒体帧；P1/P5 可单独回退。
