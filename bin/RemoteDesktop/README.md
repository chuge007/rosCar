## 0.9 公网低延迟传输

0.9.0 按四个阶段完成了公网视频链路升级：

1. 打洞失败时使用 AES-256-GCM 加密的 UDP 视频中继。
2. 接收端按秒反馈丢包率和 RTT；丢包时请求关键帧并自动降低码率/帧率，稳定后逐步恢复。
3. 使用两个服务器探测端口判断端点无关/目标相关映射，登记 IPv4/IPv6 多候选，并尝试 UPnP UDP 映射。
4. 接入真正的 QUIC Datagram 视频中继。视频链路会自动按 `P2P UDP → QUIC → 加密 UDP 中继 → 独立 TCP 中继 → 控制 TCP` 回退。

0.9.1 针对滚动、刷新和窗口切换时产生的大画面突发进行了低延迟修复：

- UDP/QUIC 视频不再把一帧的全部分片瞬间塞入网卡，而是按当前目标码率使用令牌桶匀速发送。
- 发送队列只保留很短的实时画面；积压超过约 120 ms 时主动丢弃过期预测帧、请求关键帧，并立即降低码率和帧率。
- 接收端发现残缺帧或解码失败后停止继续解码无效预测帧，等待新的 IDR 关键帧后立刻恢复。
- 大关键帧按“最后一个分片的空闲时间”判断超时，不会因为匀速发送超过旧的 250 ms 总时限而被提前清除。
- 丢包超过 30% 时立即快速降档；恢复过程更保守，避免在临界带宽附近反复升降造成数秒卡顿。
- H.264 VBV 缓冲由约 1 秒缩短为约 250 ms，降低场景突变时的编码突发量。

0.9.2 参考成熟远程桌面的“实时优先”思路重新实现了端到端 QoS；没有复制 RustDesk 源码：

- 原画仍保持屏幕原始分辨率，不再用降低分辨率掩盖带宽问题；FPS 和码率作为可动态调整的质量上限。
- 公网原画会以原始像素、15 FPS、8 Mbps 保守起步，网络稳定后每次只增加 1 FPS 和 150 kbps，逐步恢复到 30 FPS / 16 Mbps 上限。
- 接收端增加最多 3 帧的有界解码队列。队列积压时丢弃旧预测帧、重置参考链并请求新关键帧，避免刷新后播放数秒前的旧画面。
- 发送端同时依据丢包、RTT 相对最低值的排队延迟、解码队列深度、解码速度和解码负载调整 FPS/码率。
- 严重拥塞在一个反馈周期内快速减速；稳定恢复需要连续样本，并采用慢速加档，减少临界带宽下的反复卡顿。
- 画面顶部新增“解码队列 / 负载”，诊断日志新增完整 QoS 样本，可区分网络拥塞与接收电脑解码不足。

0.9.3 修复了实机日志发现的静止画面 QoS 误判：Desktop Duplication 在桌面没有变化时只产生少量新帧，低解码 FPS 本身不再被当作解码器落后。接收端只有在解码队列达到 2 帧或解码负载达到 70% 时才报告解码压力；队列为 0～1、负载较低且网络稳定时允许画质正常恢复，避免原画被错误地一路压到 1 Mbps。

0.9.4 修复公网弱网下控制端断开后被控端仍停留在连接状态的问题：主动断开时先把 `ControlEnd` 刷入 TCP，再关闭连接；会话控制通道每 2 秒交换应用层心跳，连续 10 秒收不到对方任何控制数据时自动结束会话、停止捕获并恢复被控端窗口。即使控制端进程崩溃、断网或中继没有及时转发关闭事件，被控端也不会无限保持被控状态。

0.9.5 将全屏退出键由 F11 改为 Esc。全屏只能通过“全屏控制”按钮进入，进入后 Esc 快捷键才启用；退出全屏后 Esc 恢复为普通远端按键，不会在窗口模式下被本程序占用。

0.9.6 重构状态显示：远程画面不再覆盖“控制中”、当前链路和性能指标；“控制中 / 被控制中 / 连接中”与“局域网直连 / UDP 直连 / QUIC、UDP、TCP 中继”等链路状态移动到底部状态栏最右侧。顶部新增“帮助”菜单，其中“显示网络信息”控制左侧公网、NAT、UPnP、RTT、丢包、FPS、码率和解码信息的显示，默认关闭并记住用户选择；“信息”弹窗汇总本次运行的状态栏历史和磁盘网络诊断日志。进入全屏后菜单栏、侧栏与状态栏一起隐藏。

底部状态栏最右侧持续显示当前控制角色和链路。需要查看 `RTT / 丢包率 / FPS / 码率 / 解码队列 / 解码负载` 时，在“帮助”菜单中开启“显示网络信息”。`LanRemoteQt-P2P.log` 记录候选、打洞发包、QUIC 助手错误和 QoS 调整，也可以通过“帮助 → 信息”直接查看。

传输设计见 `TRANSPORT_ARCHITECTURE.md`。

0.7.2 删除服务器公钥输入框，首次连接时自动验证并固定服务器身份；用户只需填写服务器地址、端口和服务器生成的组密钥。0.7.1 修复公网中继连接被错误判定为 `target is busy` 的问题。

- 在“公网服务器设置”中只需填写服务器地址、TCP 端口和网络组密钥。
- 使用相同服务器与组密钥的设备会出现在同一个设备列表中。
- 同一局域网发现到相同设备时优先使用局域网直连。
- 不同局域网的设备通过服务器配对并建立透明中继。
- UDP `45680` 登记视频候选、协调打洞并提供加密 UDP 视频中继。
- UDP `45681` 从第二个服务器端点探测 NAT 映射类型。
- UDP `45682` 承载 QUIC Datagram 视频中继。
- H.264 UDP 数据使用 AES-256-GCM 分片加密，限制单个数据报大小以避免 IP 分片。
- TCP 回退模式使用独立控制和视频中继，视频拥塞不会阻塞输入控制。
- 服务端使用 P-256 签名证明身份；客户端首次连接时自动固定服务器身份，发现身份变化时拒绝连接。
- 组密钥使用 HMAC-SHA256 挑战认证，客户端中继数据使用 AES-256-GCM 端到端加密。
- 组密钥在 Windows 本机使用 DPAPI 加密保存。
- UDP/QUIC 接收端根据包序号计算丢包；控制通道反馈 RTT、请求关键帧并驱动码率/帧率自适应。

服务端源码位于 `D:\Lz\LanRemoteServer`。在没有购买公网服务器时，可以在本机启动 Windows 服务端并填写 `127.0.0.1:45679` 完成双实例测试。购买 Ubuntu 公网服务器后，只需要部署相同服务端并把客户端地址换成公网 IP。

P2P 能否成功取决于双方 NAT 和防火墙。目标相关映射（常见于对称 NAT/部分 CGNAT）通常无法稳定打洞，此时会自动使用 QUIC；若 UDP 被网络完全封锁，再回退 TCP。

LanRemoteQt 是一个面向 Windows 的 Qt 5 远程控制原型。每个运行实例都同时具备控制端和被控端能力；局域网可直接使用，也可连接自建服务器发现和控制不同局域网中的设备。

## 当前功能

- UDP 广播自动发现同一局域网设备
- 单击设备立即建立 TCP 点对点连接
- 被控端免确认接受连接
- Windows Desktop Duplication（DXGI）高帧率桌面捕获
- FFmpeg H.264 硬件编码与解码
- 自动选择 Intel QSV、NVIDIA NVENC 或 AMD AMF
- 鼠标、滚轮和基础键盘控制
- 强制 `NoProxy`，不受 Windows 系统代理影响
- 连接超时、断线恢复和主动断开
- 被控时自动最小化本程序，关闭按钮不会误断开当前被控会话
- “禁止别人控制本机”开关；开启后仍可主动控制其他设备
- 可修改向局域网广播的本机名称
- 可为每个远端设备设置仅在本机显示的备注名
- 控制端可点击“全屏控制”进入独占全屏，并按 Esc 退出
- 控制端或被控端将文件拖入本程序窗口，即可按当前角色双向传输
- 双向同步文字、截图/图片以及复制的文件剪贴板

被控端会明确显示“正在被控制”，并保留立即断开按钮。局域网直连沿用兼容旧版本的未加密通道，只应在可信局域网使用；公网服务器连接会验证服务器签名和组密钥，并对会话数据进行端到端加密。

## 画质档位

| 档位 | 最大分辨率 | 帧率 | H.264 目标码率 |
|---|---:|---:|---:|
| 流畅 | 1280×720 | 20 FPS | 3.5 Mbps |
| 清晰（默认） | 1920×1080 | 30 FPS | 9 Mbps |
| 原画 | 屏幕原始分辨率 | 30 FPS | 16 Mbps |

网络发送或本机解码积压时会跳过旧帧，优先保持控制响应和低延迟。原画档不会动态降低分辨率，但公网连接会动态调整帧率和码率；顶部显示的当前值可能低于档位上限。一次画面突发后的短窗口内丢包率仍可能升高，程序会在一个反馈周期内减速并请求关键帧，而不是继续排队播放旧画面。静止桌面帧率低属于正常行为，不会触发降速。

## 构建环境

- Qt 5.15.2 MSVC 2019 64-bit
- Visual Studio 2022 C++ 工具链
- Rust/Cargo（用于构建随程序分发的 `lanremote-quic.exe`）
- FFmpeg 7.1 静态库
- libyuv 静态库
- Windows SDK：D3D11 / DXGI 1.2

本机依赖目录：

```text
D:\Lz\vcpkg\installed\x64-windows-static
```

使用 Qt Creator 打开 `LanRemoteQt.pro`，必须选择 `Desktop Qt 5.15.2 MSVC2019 64bit` 套件。MinGW 套件不能链接当前 FFmpeg MSVC 静态库。

如果“问题”面板显示 `Desktop Duplication + FFmpeg build requires the Qt MSVC 2019 64-bit kit`，说明当前仍选中了 MinGW。打开左侧“项目”页，在“构建和运行”中启用 `Desktop Qt 5.15.2 MSVC2019 64bit`，切换到该套件后删除原 MinGW 构建目录，再重新运行 qmake。

也可以直接双击 `build-msvc.bat`，绕过 Qt Creator 的当前套件选择。

`build-msvc.bat` 会先构建 QUIC 助手，再复制到 Qt 可执行文件目录。直接在 Qt Creator 中构建时，需要先在 `quic-helper` 目录执行 `cargo build --release`，并把 `target\release\lanremote-quic.exe` 复制到 `LanRemoteQt.exe` 同目录。发布包已经包含该文件，测试电脑无需安装 Rust。

工程固定使用 Release，因为本项目的 FFmpeg/libyuv 是发布版静态库。若看到 `LNK2038`、`RuntimeLibrary MD/MDd` 或 `_ITERATOR_DEBUG_LEVEL 0/2`，请先运行 qmake，再执行“清理项目”和“重新构建项目”；不要复用旧的 Debug `.obj` 文件。

命令行构建：

```bat
call "D:\Program Files\Microsoft Visual Studio\2022\Community\Common7\Tools\VsDevCmd.bat" -arch=x64
D:\QT\5.15.2\msvc2019_64\bin\qmake.exe LanRemoteQt.pro
nmake
```

## 使用

1. 在两台同 WiFi 的 Windows x64 电脑上运行相同版本。
2. 首次运行时允许 Windows 防火墙访问专用网络。
3. 等待设备出现在左侧列表。
4. 选择画质后，单击设备即可直接连接并开始控制。
5. 任一端点击“断开连接”可结束会话。

如果能发现设备但无法连接，请检查 TCP 端口、防火墙和路由器的无线客户端隔离。默认 UDP 发现端口为 45454，首选 TCP 端口为 45678。

## 名称与被控权限

- 点击“修改本机名称”后，新名称会立即通过 UDP 广播，其他电脑会看到该名称。
- 选中远端设备后点击“修改所选设备备注”，或直接右键设备，可设置仅保存在当前电脑上的备注名；留空即可恢复对方广播名称。
- 开启“禁止别人控制本机”后，本机仍可控制其他允许被控的设备，但会拒绝别人对本机的控制请求。
- 被控会话开始后，本程序在被控电脑上自动最小化。被控期间点击本程序关闭按钮也只会最小化；需要结束会话时，恢复窗口并点击“断开连接”。
- 控制成功后点击“全屏控制”，可隐藏设备栏与状态栏，让被控画面占满当前屏幕；按 Esc 退出全屏。

## 文件与剪贴板

- 当前电脑作为控制端时，把一个或多个文件拖入本程序窗口，会保存到被控电脑的“桌面\LanRemoteQt Received”。
- 当前电脑作为被控端时，恢复本程序窗口并把一个或多个文件拖入，会保存到控制端的“下载\LanRemoteQt Received”。
- 在远端资源管理器中选中文件并按 Ctrl+C，会自动分块传回控制端并进入本机剪贴板。
- 两端复制的文字和图片会自动同步。被控电脑使用 Print Screen 或截图工具后，控制端可直接在聊天软件、画图等程序中粘贴。

单个文件按 64 KB 分块传输，接收文件使用安全临时文件写入，完成后再落盘；同名文件不会被覆盖。剪贴板文字上限为 1 MB，图片 PNG 数据上限为 24 MB。

## 限制

- 当前捕获主显示器。
- Desktop Duplication 在安全桌面、锁屏界面及部分受保护内容上可能不可用。
- 被控电脑必须具有 FFmpeg 支持的 H.264 硬件编码能力。
- QUIC 当前用于实时视频 Datagram；控制、剪贴板和文件仍走可靠的端到端加密 TCP 通道。
